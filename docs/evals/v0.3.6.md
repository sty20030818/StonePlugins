## 判定标准

1. 只有规则、方法或工程判断实际改变修改所有者、方案范围、抽象或契约、风险边界、兼容策略或验证方式时才显示工程依据。
2. 简单单一影响使用单行列表项；默认用“通俗决定 + 准确方法名”和“事实 → 决定 → 结果”的双行结构。
3. 真实竞争方案影响选择且正文尚未解释时才展开优缺点；至少三个方案比较相同字段时才使用表格。
4. 一个任务只显示一个工程依据区块，通常列 1～3 个独立影响；同一事实和决定上的相近方法必须合并。
5. 没有准确具名方法时标为“工程判断”；Emoji 只帮助扫读，文字必须独立可懂。
6. 只被注入、读取、与主题相关或事后可贴标签不算采用；纯文案等无实际影响场景不显示。
7. 加粗标签的标点位于强调标记外，避免标签紧贴正文时显示成 Markdown 字面量。

## 结论

候选覆盖了静默、精简单行、多个独立方法、真实方案取舍和无具名方法五种展示路径。Hook 继续由一个无状态入口管理三个事件，源码改为 `.ts`、发布产物改为 `.js`；插件局部 `package.json` 和独立缓存测试保证安装后 ESM 语义不依赖仓库根目录。

插件局部 `package.json` 属于 Node 启动边界；若缓存损坏使 Node 在 Hook 入口执行前退出，脚本无法返回结构化安全错误，需要重新安装插件恢复。
