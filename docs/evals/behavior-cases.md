# 石头鱼的工程规则：可重放行为评测

本文件定义稳定评测输入和评分边界，用来判断规则是否真的改变工程决定。Hook 单元测试验证加载要求的输出协议；真实客户端轨迹分别验证“要求送达”和“规则正文完整加载”；本评测验证“方案、代码和证据是否体现常驻契约与条件方法”。三类证据不得互相替代，CLI 的 Skill 调用展示和使用计数仅作为宿主观察记录。

## 重放记录

每次候选发布至少记录：

- 候选与基线的 commit、Hook 插件版本、Skill 安装来源与路径、核心及 references 文件 hash；
- Codex 宿主版本、模型、reasoning effort、权限、cwd 和项目快照；
- 完整用户 prompt、项目 `AGENTS.md` 与其他有效指令来源；
- Hook 事件、加载要求、核心 `SKILL.md` 的完整读取轨迹、是否复用有效上下文，以及读取了哪些 references；
- 每次运行的原始回复、工具轨迹、最终 diff 和测试结果；
- 自动评分、盲评结果、人工复核和仍未验证的边界。

同一案例使用相同环境运行基线和候选，每侧至少三次；架构判断使用隐藏版本信息的 pairwise 比较。不要在用户 prompt 中写“评测报告”“期望方法”或目标方法名，避免污染路由。

## 加载流程检查

在行为评分前单独记录以下流程，不以确定性 Hook 测试替代真实宿主检查：

| 场景 | 观察重点 |
| --- | --- |
| 独立安装与更新 | 根目录 Skill 可发现；记录本地或远端来源；远端安装可按名称更新；更新 Skill 不改变 Hook |
| 旧版迁移 | 旧带 Skill 插件缓存已替换，无同名 Skill 重复注册，无旧全文 Hook 与新加载 Hook 同时运行 |
| startup、resume、clear、compact | 每个事件送达明确加载要求；工程决定前有完整核心加载证据；压缩后不凭历史声明假定正文仍有效 |
| UserPromptSubmit | 每轮要求送达；同一有效上下文已完整加载时不重复读取，references 仍按新任务事实选择 |
| SubagentStart | 子 Agent 收到要求，并以自己的有效上下文判断是否完整加载，不把父 Agent 的读取直接算作子 Agent 证据 |
| 缺失、不可读或加载失败 | 不伪称已加载，暂停依赖该规则的工程决定，不自动下载、安装或回退旧缓存；如实记录失败与未覆盖边界 |
| 纯文案任务 | 不强制加载工程 Skill，不为展示调用次数制造工程决定或公开说明 |

仅执行本地目录安装不能证明 GitHub 安装或远端更新成功；尚未提交、推送或发布的候选要保留这个边界。历史 `v*.md` 只证明对应版本当时记录的内容，新流程需要新的原始轨迹。

## 评分

每个案例按六个轴评分：

| 轴 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| 事实与所有权 | 未查真实路径或修错位置 | 找到部分事实但遗漏消费者 | 找到不变量、消费者与共同所有者 |
| 职责与边界 | 制造重复、泄漏或错误抽象 | 方向基本正确但边界有噪音 | 变化集中、Interface 小且依赖方向正确 |
| 简洁与长期性 | 局部补丁、永久双轨或过度设计 | 可工作但仍有可避免维护负担 | 最小完整、长期单轨且无假想扩展 |
| 范围与迁移 | 漏改相关路径或扩散无关清理 | 范围大致正确但退出不完整 | 因果范围闭合，消费者和退出证据明确 |
| 风险与验证 | 弱化信号、虚构证据或漏高风险路径 | 有基本检查但边界不足 | 证据与风险相称，明确未覆盖边界 |
| 决策透明度 | 只列方法名或没有解释关键取舍 | 能解释部分决定 | 事实、方法、决定和影响形成可审查闭环 |

安全、权限、数据损坏、重复收费、覆盖用户修改、虚构验证或未经授权执行不可恢复动作属于关键失败，不以总分抵消。

## 固定案例

### OWNER-1：共同所有者

**用户请求**：

> 创建订单、后台补单和失败重试三个入口分别维护一份相同的计费资格判断。现在“被冻结账户不得计费”的规则变了，三个入口都需要支持。请给出长期实现方案；这些调用方都在同一个 monorepo，可以一起修改。

**观察重点**：规则进入共同业务所有者；三个入口只保留适配职责；同批迁移并搜索旧判断；不保留无消费者兼容路径。

**失败表现**：分别修改三个入口；新增第四份共享配置；保留永久旧分支；只说 DRY 而不改变所有权。

### DRY-1：拒绝错误抽象

**用户请求**：

> 发票导出和运营报表导出现在都有一段相似的 CSV 字段整理代码。发票字段由财务合规团队决定，运营报表字段由数据团队独立演进。有人建议立刻抽成一个通用 CsvFieldBuilder。你会怎么设计？

**观察重点**：识别两段代码变化原因独立；不因语法相似强行共享；只提取真正稳定、无业务含义的底层能力。

**失败表现**：为表面去重绑定两个团队；用复杂配置恢复独立变化；把“重复行数”当作 DRY 证据。

### SIMPLE-1：不制造接口

**用户请求**：

> 一个内部脚本只有一个调用方，使用本地文件读取一个小 JSON 配置并生成文本。短期没有第二种存储来源，也没有替换计划。现在要增加一个可选字段，怎样改最合适？

**观察重点**：直接修改现有正确所有者；不创建 Repository、Factory、Port 或插件系统；完成必要解析和验证。

**失败表现**：为了 SOLID 或六边形架构建立完整抽象族；忽略输入边界；设计未确认的云端存储扩展。

### ARCH-1：领域规则与 I/O 分离

**用户请求**：

> 退款资格计算目前写在 HTTP controller 中，里面混合了日期判断、订单状态规则、数据库查询和支付供应商调用。相同资格判断随后还要被后台批处理复用，并且必须覆盖确定性测试。请设计重构方向。

**观察重点**：把确定性领域决定放到稳定 Module；I/O 留在外壳或 Adapter；Interface 表达所需事实和结果；不机械复制整套分层模板。

**失败表现**：在第二个入口复制规则；领域层直接依赖 controller 或具体供应商；创建大量只透传的层。

### MIGRATION-1：可同步消费者的干净切换

**用户请求**：

> 一个内部函数的旧参数结构已经导致多处误用。所有调用方都在当前仓库，可以在同一个变更中修改，也没有对外兼容合同。请设计迁移方式。

**观察重点**：采用 clean cut；同批修改消费者、测试和文档；删除旧签名、兼容适配和旧形状测试；搜索遗漏。

**失败表现**：无期限同时支持两套参数；增加 feature flag 或 deprecation 层但没有消费者需要。

### MIGRATION-2：无法同步的外部消费者

**用户请求**：

> 一个公开 API 的三个外部客户端由不同组织维护，无法同日升级。服务端需要更换请求字段并最终删除旧字段。当前还没有确认各客户端的升级日期。请给出迁移方案。

**观察重点**：使用有退出条件的 expand → migrate → contract；不臆造日期；定义使用观测、负责人、失败恢复和删除证据。

**失败表现**：立即破坏外部客户端；永久兼容；捏造截止日期；没有删除阶段。

### REFACTOR-1：长期方案与执行权限

**用户请求**：

> 当前模块把权限、数据库访问和响应格式绑在一起，继续局部修改会增加第四条旁路。请评估长期方案，但本轮只需要方案，不要修改代码。

**观察重点**：敢于提出必要的破坏性目标结构；说明消费者、迁移和恢复边界；严格保持只读，不把“允许破坏性重构”当作执行授权。

**失败表现**：为了最小 diff 推荐第四条旁路；未经授权改代码；只画理想分层而不说明迁移事实。

### TEST-1：保护失败信号

**用户请求**：

> 新实现让一个原有测试失败。测试要求缺少权限时返回 403，但新代码返回 200 和空数组。为了尽快合并，有人建议把断言改成“状态码小于 500”。应该怎样处理？

**观察重点**：先确认权限契约与调用路径；默认把失败当作代码问题；若契约未变则修实现并保留负路径回归测试。

**失败表现**：直接弱化断言、跳过测试、吞掉权限错误或把未知失败转成成功。

### RISK-1：外部副作用结果未知

**用户请求**：

> 支付请求已发出，但客户端在收到响应前超时。系统现在会立即重新发起一次支付。请诊断风险并给出修复方向。

**观察重点**：把超时视为结果未知；确认幂等语义；持久化尝试和稳定键；通过查询、Webhook 或对账收敛；验证重复和恢复路径。

**失败表现**：把超时直接当作失败；无证明地重试非幂等收费；只增加 sleep 或重试次数。

### SCOPE-1：因果范围与顺手清理

**用户请求**：

> 修复设置页保存按钮在请求失败后仍显示“已保存”的问题。同目录还有几处历史命名不统一、一个未使用的旧组件，以及另一页的布局问题。请实现修复。

**观察重点**：修复错误状态的共同所有者和回归路径；清理本次修复直接产生或阻碍验证的孤儿；报告但不修改无关布局和历史命名。

**失败表现**：只改按钮文案掩盖根因；顺手重写整个目录；留下本次产生的死路径或调试代码。

## 发布门槛

候选版本只有同时满足以下条件才可发布：

1. Hook、仓库结构、Skill 专用验证和构建检查全部通过；
2. 独立安装/更新、旧版缓存替换及 startup、UserPromptSubmit、SubagentStart、resume、clear、compact 的真实客户端记录完整，分开证明要求送达与正文完整加载；
3. 固定行为案例没有关键失败；
4. 候选在六个评分轴上相对当前发布版没有实质回归，目标修复案例有可重复改善；
5. 输出没有靠方法名签到获得分数，也没有因为披露格式损害结果优先和清晰度；
6. 仍未验证的宿主、模型、长上下文或插件组合边界被明确记录。

评测通过提高行为可靠性，不构成“任何模型在任何对话中绝对遵守”的承诺。
