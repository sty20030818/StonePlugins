## 判定标准

1. 每个工程任务轻量检查常驻原则，但检查不等于增加抽象、文件或架构层。
2. 只有方法论、工程判断或用户约束实际改变所有者、范围、契约、风险、兼容或验证时才显示决策区块。
3. 按独立决策组织；展示所有实际改变用户判断的方法并逐项说明准确分类和具体贡献，不设 `1～3` 项固定上限。
4. 方案阶段使用“预期影响、验证计划”，交付阶段使用“方案影响、验证证据”，不混淆预期与事实。
5. 简单决定保持单行；普通决定使用标题与列表；复杂或大量决定先用紧凑索引覆盖，只展开高风险、需确认或有真实竞争的项。
6. 不虚构代价、备选方案、方法名或验证结果；完整检查事实仍由交付正文的“验证”持有。
7. 更高优先级的输出约束优先；压缩时不混淆独立决定，无法完整披露时说明省略边界。

六个案例当时均符合判定标准，但由于缺少完整重放材料，本版本不把 `6/6` 表述为可重复的回归通过。可重复行为门禁需要先固化中性 prompt、完整指令边界、模型信息、原始输出和判定器，再用于后续版本比较。

首轮评测发现简单输出遗漏分类，普通与复杂输出会把不同方法及分类混在同一项。候选随后增加逐项分类格式，并让多方法采用或分类不确定的任务读取方法论索引。第二轮又发现加粗示例被行内代码包裹、交付中的验证决策误用“方案影响”；移除反引号并收紧“验证证据”标签后，使用新的隔离 Agent 重跑通过。前两轮不计入最终通过数。

四决策案例第一次运行时，场景要求明确截止时间却没有提供合同或发布日期，输出擅自填写了具体日期，因此判为失败。候选随后在迁移 reference 中要求兼容日期必须来自已确认计划；使用“具体日期尚未确认”的新隔离案例重跑后，四项决定完整展示且日期保留为待决策。失败轮不计入最终通过数。

## 结论

探索性观察覆盖静默、简单多决定、复杂方案、已完成交付、非方法论依据和四项独立决定六种路径；确定性门禁覆盖注入结构、体积和损坏缓存。当前架构继续保持一个公共 Skill、四个按需 references 和一个共享 Hook adapter；没有增加运行时依赖、SQLite、额外公共 Skill 或新的 Hook 事件。大规模披露与跨插件组合仍需在后续可重放评测中验证。
