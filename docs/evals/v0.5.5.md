# v0.5.5 验证记录

日期：2026-11-02。基线为正式发布的 v0.5.4。正式发布状态以 [GitHub Release](https://github.com/sty20030818/StonePlugins/releases/tag/v0.5.5) 和 [tag 流水线](https://github.com/sty20030818/StonePlugins/actions/workflows/validate.yml)为准。

## 原始问题与修复

用户提供的 Codex 截图中，任务仍在执行，“为什么这么做（石头鱼的工程规则）”已经作为中途消息展开。原规则只要求在“结果或推荐后”说明，没有限定最终回复；中途汇报结果或推荐也可能触发。Hook 仅注入规则，不负责处理或移动模型消息。

- 核心明确该说明仅在本轮最终回复展示，中途不输出标题或完整说明；必要的依据、风险、影响与待确认事项仍及时用普通文字说明。
- 每轮短提醒同步展示边界；工程规则继续贯穿执行，不等到最终回复才应用。
- 活动行为规范新增 TIMING-1，检查中途与最终原始消息，并将只隐藏标题、遗漏必要确认或缺少最终说明列为失败。

## 验证入口与边界

`npm run check` 的 typecheck、build、仓库校验与 10 个 Hook 测试全部通过。Codex CLI 0.164.0 在临时空白配置目录中从候选仓库安装 `stoneplugins@stonefish`，回读为 0.5.5、已启用；缓存的 11 个文件与候选逐字节一致。直接从该安装缓存执行 SessionStart、SubagentStart 和 UserPromptSubmit，完整核心与短提醒均带有最终回复的展示边界，未改变真实用户配置。

逐轮提醒为 288 UTF-8 bytes，仍在 300-byte 上限内；隔离安装路径下的生命周期上下文为 7,324 bytes，仍在 8,000-byte 上限内。路径长度会影响上下文字节数，这些值不是模型 token 统计。

发布使用 `npm run check`、`npm run validate:release` 和 tag CI；版本字段、生成的 JavaScript Hook 与包内资源一并核对。安装后回读缓存版本、文件内容与 Hook 输出，不能用安装前的聊天上下文证明新版本已加载。

确定性检查验证上下文协议、正文完整性和字节预算，不能证明模型稳定遵守展示时机。真实 Codex 多步骤轨迹与界面展示须单独记录；不继承 v0.5.4 的格式行为样本，也不宣称失败概率已经下降或永久遵守。

通用 Skill 校验器因本机 Python 缺少 PyYAML 未运行；仓库原生校验覆盖本包的 frontmatter、资源引用和分发结构，无需为本次修复新增依赖。
