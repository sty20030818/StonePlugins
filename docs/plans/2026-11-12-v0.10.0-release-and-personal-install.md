# StonePlugins 新版正式发布与个人安装方案

用户已确认版本为 `v0.10.0`；本地候选准备批次仅覆盖资料同步与验证，后续候选提交、远端推送和 CI 按版本评测中的逐批授权与实际结果接续。打 tag、创建 Release 与个人安装仍需各自范围，不能因方案存在而自动执行。当前本地结果从[v0.10.0候选验证](../evals/v0.10.0.md)读取。沿用本仓 `docs/plans` 的方案所有权；实际版本验证与发布/安装结果由新的 `docs/evals/v0.10.0.md` 在执行时记录，不预填通过，不改写旧评测。

## 推进顺序与门禁

以下按成果依赖顺序推进，是操作批次，不新增Phase或Task状态对象。每一步只在其范围获准后执行。

### 1. 准备可审阅的v0.10.0候选

先复核两仓实际HEAD、已有修改和远端状态。在本仓同步根package.json版本、package-lock.json顶层及根包版本、插件manifest版本；插件根package.json目前仅拥有ESM/私有包语义，不为凑版本添加无消费者字段。marketplace名与插件ID保持原有值。

CHANGELOG增加本版本的实际选入成果，README增加新版本当前说明并只更新当前安装示例；保留v0.9.2等历史章节中的准确版本，不批量替换旧tag。建立新的docs/evals/v0.10.0.md，记录精确候选身份、已有证据的适用范围和尚未执行项；待实际发生后追加真实结果。

候选必须继续使用受支持完整包导入，不手改生成的lib、rules或安装缓存。若发现需要修复程序/规则，回到相应作者仓完成必要回归并形成新的真实固定提交，再重新明确受影响证据，不能沿用原1965e56身份。

门禁：所有版本字段一致，十一项技能及配套资源完整，规则与指南来源准确，用户已有评测和暂存边界保持。新文件在用户批准的正常提交中进入Git跟踪后，才能把其发布门禁计为通过；不为消除未跟踪报错擅自暂存。

### 2. 使维护者可取回上游固定来源

远端写入获准后，先审查并推送包含1965e56、6595438的StoneDocs正常提交链，由有权访问私有仓库的维护者重新从远端精确读取两份来源。无需为了插件发布另发同名StoneDocs V2版本或npm包；目标编号、CLI版本和插件版本独立。

运行/等待实际推送HEAD的StoneDocs现有CI，核对代码及构建输入与受检产物对应。若CI验证的是较新文档HEAD，就如实记录该HEAD，不声称较早的来源commit单独跑过同一CI。随后将StonePlugins候选提交推送到main，核对远端HEAD和候选内容，再等待其main CI。

门禁：维护者能认证取回固定来源、不是working-tree；包内声明与对应原文/构建输入一致；上游与消费者CI对应实际推送对象。公开消费者应能从StonePlugins固定tag取得完整可运行包，不要求其访问私有StoneDocs，也不声称源码公开可重建。出现权限、来源或远端并发变化时停止相关写入，不强推或换成latest掩盖缺口。

### 3. 验证最终候选与固定tag

在最终候选运行npm run check（类型、Hook构建、仓库校验及回归）、git diff --check，并确认重建Hook没有生成物漂移。版本资料经正常提交进入跟踪后运行npm run validate:release；它不能替代远端来源可取回、CI或宿主行为。

候选内容无相关变化时，复用StoneDocs原有程序回归、恢复和十二场景，不重跑整套产品测试或三次原样模型样例。新版本完整包需从精确候选/实际tag取得，核对产物清单、固定资源、指南及不依赖作者checkout的读取；版本和包装变化需要覆盖新缓存路径。

main CI通过后，核对v0.10.0尚未占用，再建立与manifest同版的annotated tag并推送。现有Validate工作流在Node22.18.0和24上检查：tag与manifest版本一致、类型、构建、生成脚本已跟踪且无漂移、仓库校验、正式发布门禁和回归。必须等待该tag实际CI成功；main成功不能代替tag成功。

门禁：本地完整检查与release模式通过；实际远端tag指向选定提交，两个Node矩阵通过。任何来源错误、覆盖用户内容、契约回退或关键失败都阻断放行；不能以历史0.9.2门禁通过代替。

### 4. 形成正式公开发布事实

只在以上门禁与公开发布授权具备后创建v0.10.0 GitHub Release，标明普通正式版、精确tag/提交、选入内容、旧v1项目不会自动升级、明确的验证范围与遗留。独立读回tag、Release状态及链接。现有CI只验证，不自动创建Release，也不自动向公共插件目录提交审核。

本方案的“正式发布”是既有GitHub仓库/marketplace分发渠道；提交OpenAI公共插件目录是另一种产品分发范围，不混入本版。若授权仅到发布而未包含个人安装，就停在该真实边界。

### 5. 原生更新个人固定版本

先重新读取stonefish来源、ref、启用状态、旧包内容和相关配置；以私有恢复材料保留旧完整包及本次会变的精确配置。历史安装器曾删除旧缓存，不能假设旧0.9.2缓存永远可作为回退来源。恢复不得用旧全量配置覆盖后续MCP、其它marketplace、插件或个人规则变化。

当前来源应继续是同一GitHub仓库，将固定ref明确切到v0.10.0。官方CLI有marketplace add/list/upgrade/remove及plugin add/list接口，但没有可假定存在的任意plugin update命令；固定ref的upgrade不会替用户选择下一版本。参见[OpenAI开发命令](https://learn.chatgpt.com/docs/developer-commands)。执行时查看本机help，优先受支持的精确来源更新；若同名来源拒绝换ref，按已验证的原生remove/add路径只处理stonefish，再plugin add。不要叠加同ID的本地来源、手改缓存或改为跟随main。

安装后核对实际缓存与远端tag的包内容逐项一致，manifest=0.10.0、CLI=0.2.0、规则契约=2、来源匹配；新进程应发现十一个技能，入口均来自新安装。安装存在、enabled和文件版本分别读回，不靠当前聊天缓存宣称更新成功。根据[OpenAI插件说明](https://developers.openai.com/plugins/build/plugins)，安装与Hook信任独立；按[Hook原生审核](https://learn.chatgpt.com/docs/hooks)检查三个实际定义，只有需要审核的项才经正常界面/接口确认，不直接写trusted hash或绕过信任。

在新会话中选择与本版变化相称的少量真实用例：总体技术设计/架构重审的自然语言入口；v1项目继续本地规则；已采用v2项目读取本地方法并按文件接续；缺失方法/未知身份只暂停依赖工作。这些可以在临时资料中做，不再次升级StoneFlowNext或其它产品。记录实际读取路径、可取得的模型/effort、有效指令与观察；未知元数据如实留缺，不能据此做因果或稳定率结论。

同批检查正常startup和UserPromptSubmit的实际送达，确认核心完整、三份细则可达、只有一份工程入口。Hook内容及加载机制未变化时，其余生命周期复用同版内容对应的历史证据并标明未重验；若信任/包装/上下文有新失败，只扩验受影响的resume/compact/SubagentStart等，不为凑全量次数启动额外工作。若需证明“所有生命周期均已在0.10.0重新验收”，就必须实际逐项运行，不能借复用改写成新结果。

门禁：实际固定来源安装、完整包匹配、新进程发现、本版相关语义与加载样例取得结果，个人非目标配置/其它入口保持。UI仅在实际观察后写通过；CLI检查不能证明桌面UI徽标或交互。将正式发布、安装、信任观察和真实新会话结果分别追加新版本eval，不能预填。

## 停止、恢复与兼容边界

- 公开发布前失败：停止tag/Release和个人切换，修复所属问题后只复验受影响部分；已公开的tag不移动或覆盖，真正修复需要后续版本。
- 个人安装失败：保留现场和相关配置差异，不维持新旧Hook并行；通过原生管理恢复精确旧ref和包，再核对只有一个有效来源。恢复材料只用于本次目标，不恢复整个个人目录。
- 插件回退不是项目规则降级：StoneFlowNext已经是v2，旧CLI0.1.2不能因此被当成支持v2。不得改采用记录或覆盖本地规则来迎合旧插件；必要时明确使用已验证的独立CLI0.2.0或手工Markdown继续，来源和限制须说明，不能静默换PATH。
- 更新不自动采用：任何项目的新规则采用/升级仍须自己的范围和三方比较，冲突先停。本版不再触碰StoneFlowNext产品资料或代码。
