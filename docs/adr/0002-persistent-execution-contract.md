# 以常驻执行契约驱动工程决定

## 状态

原则继续有效，旧实现记录原位归档。常驻工程执行契约、条件 references 和公开说明的职责分离继续沿用；当时的直接注入实现曾被 [ADR-0003](0003-independent-skill-and-loader-hooks.md) 替代。当前 Codex 优先目标由 [ADR-0004](0004-codex-first-bundled-engineering.md) 持有，尚未实施，不代表重新启用当时的旧 Hook、EOF 标记或预算。本文取代 ADR-0001 中“公开决策说明由核心 Skill 持有”的部分；ADR-0001 保留为 v0.3.7 历史记录。

## 背景

用户原本需要在每次工程请求后手动追加长期维护、整洁/六边形架构、SRP、高内聚低耦合、模块化、DRY、KISS、允许破坏性重构和减少兼容代码等要求。插件通过 Hooks 解决了规则送达，却逐渐把核心篇幅集中到方法论披露格式，并把常驻方法写成“轻量检查”，导致工作流可能退化为先形成方案、再做审查和方法名说明。

## 决定

将 Stonefish Engineering 设计为一个深 Module：用户只提交普通工程请求；一个公共 Skill 定义唯一常驻工程执行契约；一个无状态 Hook Adapter 在会话、子 Agent 和逐轮生命周期送达该契约；条件方法通过短信号路由读取主题 references。

所有常驻方法必须共同参与理解、设计、实施和验证。整洁架构与六边形架构的依赖和领域边界原则常驻，Port、Adapter、DDD、迁移模式等具体形态按真实信号实例化。长期破坏性方案可以主动推荐，实际执行仍受消费者、数据、恢复和授权约束。

公开决策说明是工程决定的可观察投影，不是独立执行步骤或隐藏思维记录。核心只保留触发和最小因果结构，详细 Markdown 规则放入 `decision-summary.md`。运行时方法选择放入 `method-selection.md`；完整目录、来源和晋升治理放入 `docs/methodologies.md`；固定行为案例放入 `docs/evals/behavior-cases.md`。

## 后果

- 用户无需再追加方法论提示，也无需显式选择内部 Skill 或 reference。
- 核心上下文把主要预算用于实际工程行为，不再由输出格式主导。
- 条件方法保留渐进披露，避免把方法论目录每轮全部加载。
- Hook 可以确定性验证规则送达，但模型落实仍通过代表性行为评测管理，不能承诺绝对遵守。
- 全局 `AGENTS.md` 继续承担交互、权限、项目工具与个人偏好，不复制插件工程方法，避免第二事实源。
- 新增两个内部 reference 和两个非运行时维护文档；它们分别拥有独立消费者和变化原因，避免重新形成多职责索引。
