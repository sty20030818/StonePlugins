# 石头鱼的工程规则：方法论披露与决策透明度研究

> 日期：2026-08-28
> 范围：研究 AI 编码助手怎样在最终回复中说明实际采用的工程原则、参考和决策影响，同时避免伪装或暴露 chain-of-thought、方法名堆砌及固定格式噪音。
> 证据边界：外部结论只采用 OpenAI 官方文档与 Model Spec、NIST 标准/框架、原始研究论文和方法作者原文。NIST 的解释原则不是针对 Codex 回复格式的专门规范，本文只把它作为评估解释质量的可迁移框架。
> 本地快照：当前插件由 `SessionStart`、`SubagentStart` 注入核心正文，`UserPromptSubmit` 注入固定短提醒，references 按条件读取；现有评测关注正确决策与正确路由，而不是方法名复述。当前行为以核心 Skill、references 和版本化评测为准。

## 结论先行

1. **不要用“非平凡工程任务”作为展示门槛。** 它没有稳定边界：一行根因修复可能真正使用了所有权原则，一次很长的资料整理却可能没有工程方法改变决策。更准确的门槛是：**某项原则是否实质改变了修改所有者、方案范围、抽象或契约、风险边界、兼容策略或验证方式。**
2. **最终回复展示的是“工程决策依据”，不是“内部思维过程”。** 推荐压缩为“可核查事实/风险 → 采用原则 → 导致的具体决定或验证”，不复述逐步思考，也不声称这是模型真实、完整的推理轨迹。
3. **只有“真用上了”才显示。** 仅被 Hook 注入、读取到 reference、与任务主题相关，或事后能贴上 `KISS`、`DDD`、`SOLID` 等名称，都不算采用。无法指出具体决策影响时就不显示。
4. **只显示一个工程依据区块，其中可以有多项独立影响。** 通常列 1～3 项；同一事实、同一决定上的相近原则必须合并。重点是决定和证据，不是方法论库存。简单任务可以完全没有该段。
5. **第一版不增加 `Stop` Hook。** `Stop` 能读取最终消息并要求 Codex 继续，但只能机械发现缺少某种文本，无法证明原则真的参与了决定。现在强制它会更容易制造方法名补写、延迟、额外 token 和空洞合规。
6. **推荐措辞是“按石头鱼的工程规则，本次采用……”，而不是“参考了……”。** “参考”只说明相关性；“采用 + 具体影响”才形成可审查的决策声明。

推荐的单行格式：

> **工程依据（石头鱼的工程规则）：**“正确所有者”——三个入口都经过 `SessionManager`，所以在共享创建路径统一修复，并验证三个入口；没有在各调用点重复加判断。

它不证明模型的隐藏推理过程，却把用户真正需要审查的四件事放在一起：项目事实、原则、决定和证据。

## 一、先区分四个容易混淆的概念

| 概念 | 回答的问题 | 是否适合默认展示 |
| --- | --- | --- |
| 规则被注入/文件被读取 | Agent 是否有机会看到规则或 reference？ | 不单独展示；这是加载与排障证据 |
| 方法与任务相关 | 这项方法是否可能适用于任务？ | 不展示；相关不等于采用 |
| 工程决策依据 | 哪个事实触发哪条原则，并使决定发生了什么变化？ | 真正影响决定时简短展示 |
| chain-of-thought | 模型生成答案时的内部逐步推理 | 不要求、不伪装、不作为可靠审计记录 |

用户想解决的是第三项。当前 Hook 已解决第一项的大部分问题；继续把“已注入核心规则”写进每次回复，不能回答哪条规则改变了什么。

## 二、一手资料给出的共同边界

### 2.1 OpenAI：直接给结论，必要时补充 rationale 和审计摘要

OpenAI Model Spec 把隐藏 chain-of-thought 定义为可能供模型内部使用、但不直接暴露给用户或开发者的消息；它最多可能以摘要形式出现。该规范同时要求助手对知识、能力、动作及重要副作用保持坦率；细节过多时，应先给关键摘要，并在需要时提供更详细的 audit trail。[OpenAI Model Spec：Hidden chain-of-thought 与 Be honest and transparent](https://model-spec.openai.com/2025-12-18.html)

同一份 Model Spec 的表达原则是：先直接回答；合适时再补充 rationale 和重要替代项。高质量答案加解释优于先铺开思考过程再给结论。[OpenAI Model Spec：Be clear and direct](https://model-spec.openai.com/2025-12-18.html)

这给本插件两个直接约束：

- 最终回复可以说明**可公开、可审查的判断依据**，但不要称它为“真实思维链”或逐步复述内部推理；
- “工程依据”应在结果之后保持短小，详细证据或长期架构记录只在风险和任务需要时展开。

OpenAI 当前模型指南还建议测试最终消息是否包含所需证据、引用和 caveat，而不能只验证中间工具输出；这支持把“工程依据是否准确、是否该出现”纳入代表性评测。[OpenAI Model Guidance：Assess the final answer](https://developers.openai.com/api/docs/guides/latest-model)

### 2.2 NIST：有解释还不够，解释必须有意义且准确

NIST IR 8312 提出四项解释原则：提供输出或过程的理由/证据、对目标用户有意义、解释准确反映生成输出的原因或过程，以及承认知识边界。NIST 也明确指出不存在适合所有用户和情境的单一解释形式。[NIST IR 8312, *Four Principles of Explainable Artificial Intelligence*](https://nvlpubs.nist.gov/nistpubs/ir/2021/NIST.IR.8312.pdf)

对本问题最重要的不是“必须解释”，而是后两层限制：

- **有一段解释不代表它准确。** “这次使用了 KISS、DRY、SOLID”即使听起来专业，也可能只是事后贴标签；
- **解释要面向用户当前决策。** 用户需要的是为什么修在这里、为什么选这类验证、放弃了什么，而不是方法论百科；
- **无法可靠确认时要收缩声明。** 可以说“这个决定符合/采用某条可公开原则”，不能把自述升级为对隐藏推理的完整证明。

NIST AI RMF 还强调治理动作不是固定清单，应按情境和风险裁剪；它要求透明的政策、过程与结果，并记录风险、影响及知识边界。[NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)

由此可得一个适合当前工作流的取舍：**以影响为触发器，以用户可核查事实为内容，以风险调整详细度，不把“每次必填”当成透明。**

### 2.3 原始研究：语言模型的解释可能是可信外观，而不是忠实因果记录

Turpin 等人的实验发现，模型的 chain-of-thought 解释可能系统性遗漏真正影响答案的偏置信号，并为受偏置影响的答案生成看似合理的解释；作者因此警告，解释可以“可信但误导”。[Turpin et al., *Language Models Don't Always Say What They Think*](https://arxiv.org/abs/2305.04388)

Lanham 等人通过截断、加入错误、改写和 filler tokens 等干预测试 reasoning faithfulness，发现不同任务和模型之间差异很大，也存在事后推理或模型没有按文字推理工作的情况。[Lanham et al., *Measuring Faithfulness in Chain-of-Thought Reasoning*](https://arxiv.org/abs/2307.13702)

这些论文不表示“任何模型解释都无价值”，但足以否定一个过强承诺：**不能因为最终回复声称“使用了某方法”，就把它当作该方法真实参与内部推理的证明。**

更稳妥的产品语义是：

> 这是一个受项目事实与产物约束的决策摘要，用于让用户审查结论；它不是隐藏思维链的转录，也不是单靠文字即可验证的因果归因。

### 2.4 ADR：保留 Context、Decision、Consequences，放弃每回合写完整记录

Michael Nygard 的原始 ADR 文章只要求记录“架构上重要”的决定；每份短记录围绕一组 forces/context、一个 decision、状态及正负或中性 consequences 展开。作者强调小而模块化的文档更容易阅读和维护，一个 ADR 只记录一个显著决定。[Michael Nygard, *Documenting Architecture Decisions*](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

这套结构很适合压缩成回合级摘要：

- `Context` → 当前项目事实、约束或风险；
- `Decision` → 采用的工程原则导致的具体选择；
- `Consequences` → 修改范围、被排除的替代方案、验证或已知代价。

但 ADR 本身不适合每次对话都创建。只有决定会长期影响结构、非功能属性、依赖、公共接口或构建方式时，才升级为仓库中的持久 ADR；普通任务只需最终回复中的一个简短工程依据区块。

## 三、“真用上了”的可执行判定

不再问“任务是否非平凡”，改为检查下列三个条件。三项同时成立才展示：

1. **有触发事实**：存在可指向的代码路径、消费者、契约、风险、失败证据或项目约束；
2. **有决策作用**：该原则改变了至少一项结果——修改所有者、范围、抽象/契约、风险/权限边界、兼容策略或验证方式；
3. **有可核查影响**：能用一句话指出最终做了什么、没有做什么，或新增了什么验证。

一个实用的反事实检查是：

> 如果去掉这条原则，这次方案是否可能落到另一个所有者、扩大/缩小不同范围、采用另一种契约或验证？

- 若答案是“会”，而且能指出差异，则可以披露；
- 若答案只是“这条原则也挺相关”或“最后方案恰好不违背它”，则不披露。

### 算采用

- 三个调用方都经过同一个 parser，因此按“根因与正确所有者”只修 parser，并搜索确认没有旁路；
- 外部消费者不能同步升级，因此采用 Parallel Change，明确 expand、migrate、contract 三阶段和删除旧路径的条件；
- 两个 adapter 必须满足同一行为契约，因此采用 contract tests，而不是各写一组互不等价的 happy-path 测试；
- 权限边界受影响，因此按最小权限和风险比例验证补充拒绝路径测试，而不只跑类型检查。

### 不算采用

- 核心规则在 SessionStart 时被注入，但本任务只是翻译文案；
- Agent 读取了 `architecture.md`，最终选择却完全由用户明确指定且没有架构判断；
- 实现完成后可以用 `KISS`、`DRY`、`SOLID` 中任意几个词描述；
- 方法只出现在“考虑过的备选”，没有改变最后决定或验证；
- 回复只能写“遵循最佳实践”，无法说明项目事实与具体影响。

这个边界让用户的“真用上了就显示”变成可评测规则，而不是依赖“非平凡”的模糊直觉。

## 四、推荐的用户可见格式

### 4.1 默认：单行

```text
工程依据（石头鱼的工程规则）：“{通俗的原则或方法短标签}”——{项目事实/风险}，因此{具体决定与验证}；没有{被排除的替代方案，若有价值}。
```

这比“我们参考石头鱼的工程规则，这次运用了……”更自然也更准确：

- “按”说明这是当前决策约束；
- “采用”必须接具体影响，不停留在相关性；
- 先写事实再写影响，用户可以反驳事实或判断；
- 没有实际影响时整行消失，不形成固定口播。

### 4.2 确有多个独立决策：放在同一个区块

```text
工程依据（石头鱼的工程规则）：

- “共同封闭原则”：三个入口因同一原因变化，因此把校验放入共享所有者，没有分别打补丁。
- “风险比例验证”：改动触及权限拒绝路径，因此增加未授权回归测试，而不只运行类型检查。
```

通常列 1～3 项；真正存在更多独立影响时可以继续列，但应先检查是否能够合并。不要把同义原则拆成多条，例如“根因修复”“正确所有者”“DRY”若都导向同一个共享修复，只保留最能解释决定的一项。

### 4.3 不一定要挂经典方法名

方法名有助于检索和积累共同语言，但不是展示资格。优先使用用户能理解、且与规则正文一致的短标签：

- 推荐：“正确所有者优先于最小 diff”“行为契约测试”“有退出条件的兼容期”；
- 需要检索时：“共同封闭原则（CCP）”“Parallel Change”；
- 不推荐：“SOLID + Clean Architecture + DDD + KISS + DRY”。

经典名称与当前决策之间若没有一一对应关系，宁可使用朴素规则描述。

### 4.4 证据和 rationale 的职责不同

- **证据**回答“我们看到了什么”：调用路径、测试结果、公共契约、官方文档或消费者列表；
- **rationale**回答“这个事实为什么支持这个决定”；
- **结果/后果**回答“最终改变了什么，还有什么边界”。

一条好的工程依据至少包含前两项，并尽量包含可验证结果。不要用方法名替代 rationale，也不要用一长串工具日志替代证据摘要。

## 五、为什么第一版不应强制 `Stop` Hook

OpenAI 当前 Hooks 文档说明：`Stop` 会收到 `last_assistant_message`；返回 `decision: "block"` 时不会拒绝本轮，而是让 Codex 继续，并把 `reason` 作为新的 continuation prompt。`Stop` 当前不使用 matcher，且 `stop_hook_active` 用于表明本轮是否已被继续过。[OpenAI Hooks：Stop](https://learn.chatgpt.com/docs/hooks)

它能可靠做的是**文本结构检查**，例如“要求的 JSON 字段是否缺失”；它不能仅凭最终消息判断：

- 哪份 reference 实际被读取；
- 哪项原则是否真实改变了决定；
- 某个方法名是任务中使用的，还是为了通过 Hook 临时补写的；
- 一个简单任务是否本来就不该出现“工程依据”。

因此，一开始加入强制 Hook 会带来四个副作用：

1. **假阳性**：所有工程回复都补上一条看似合规的方法名；
2. **假阴性**：文字格式存在，但事实、原则和决定没有真实连接；
3. **运行成本**：缺失时多一次 continuation、模型调用、延迟与 token；
4. **复杂度**：需要处理 `stop_hook_active`、多 Hook 并发、格式误判和失败回退。

最重要的是，它优化了“字段出现率”，不是“决策透明度”。

### 何时才考虑增加 `Stop` Hook

只有同时满足以下条件时再评估：

- 核心指令和代表性评测已经稳定；
- 真实任务中反复出现“本应披露却漏报”，且漏报造成了可观察损失；
- 已有一个可靠信号能区分“应该披露”和“无需披露”，而不是让 Hook 猜任务复杂度；
- Hook 只验证最小结构，不判断方法论真伪；
- 对 continuation 次数、延迟、token、误阻断和噪音有回归测试。

在现有插件下，这些前提尚未成立。当前最小完整方案是改核心完成规则并评测，不新增 Hook。

## 六、建议写入核心规则的候选文本

```text
当石头鱼的工程规则或按需 reference 实质改变了本次修改所有者、方案范围、抽象或契约、风险边界、兼容策略或验证方式时，在最终回复中增加一个“工程依据（石头鱼的工程规则）”区块；没有实际影响时不显示。

一个任务可以同时采用多种方法。每项只说明一个独立影响，通常列 1～3 项；每项先用一个通俗短标签点明原则或方法，再说明“可核查的项目事实或风险 → 导致的具体设计决定或验证”，正式名称只在有助于理解或检索时附上。

多项原则基于同一事实并导向同一决定时必须合并。仅被注入、读取、与任务相关，或事后能够贴上方法名，不算采用；无法说明具体影响时不显示。该摘要用于解释可公开的工程决定，不复述或声称代表内部思维过程。
```

用户可见推荐模板：

```text
工程依据（石头鱼的工程规则）：“{通俗短标签}”——{事实}，因此{决定/验证}。
```

这段应只有一个权威所有者，推荐放在核心 Skill 的“完成条件”附近。不要再复制到全局 `AGENTS.md`、每轮 reminder 和多个 reference，否则会形成重复事实源。

## 七、评测方案：先验证准确性，再追求出现率

### 7.1 固定案例

| 案例 | 预期 |
| --- | --- |
| 翻译、改一句文案、回答事实问题 | 不显示工程依据 |
| 核心规则已注入，但方法没有改变结果 | 不显示 |
| reference 被读取，但最终决定完全由用户硬约束给出 | 不为“读取过”而显示 |
| 多个调用方共享同一根因 | 显示一条“正确所有者/共同封闭”，含共享路径与验证 |
| 公共契约迁移且消费者不能同步 | 显示迁移方法、消费者事实和退出条件 |
| 权限、安全、持久化或金钱路径 | 显示真正改变风险控制或验证的原则；不能只列“安全最佳实践” |
| 提示中故意罗列 `SOLID/DDD/KISS/DRY` | 只显示真正改变决定的 0～3 项独立影响，不跟随复述 |
| 两个同义原则都支持一个决定 | 合并为一条，不重复计数 |
| 方法冲突 | 显示胜出的约束及具体影响，不把双方都列成“已采用” |

### 7.2 评分维度

1. **触发精度**：不该出现时是否保持安静；
2. **事实可核查性**：项目事实能否由代码、契约、测试或来源验证；
3. **决策连接**：原则是否解释了一个具体选择、拒绝项或验证；
4. **名称准确性**：方法名与索引定义一致，没有用名词包装普通行为；
5. **简洁度**：只有一个区块，通常 1～3 项；同一决定不重复列相近原则，没有复述整套规则；
6. **边界诚实度**：不声称披露完整内部推理，不把未验证内容写成事实。

这里应优先优化 **precision** 而不是 recall：偶尔漏掉一条低价值回执，危害小于每次都输出一段可信外观的伪解释。

### 7.3 推进顺序

1. 把候选文本加入核心 Skill，保持现有 Hook 架构不变；
2. 在固定案例上做修改前/后的隔离对照，记录该出现时的召回和不该出现时的噪音；
3. 用真实任务抽样复核“事实 → 原则 → 决定”是否成立；
4. 根据误报优先修正文案和触发定义；
5. 只有持续漏报造成实际问题时，才重新评估 `Stop` Hook 或独立诊断日志。

### 7.4 候选规则前向评测

2026-08-28 使用相互隔离、无父对话历史的子 Agent 对候选核心规则做了三类真实任务检查：

| 场景 | 结果 |
| --- | --- |
| 纯翻译 | PASS：没有显示工程依据 |
| 单实现、单调用方且无替换计划，却建议提前增加 interface/factory/config | 首轮暴露同一决定被拆成两项；收紧“同一事实与决定必须合并”后 PASS，只保留一项通俗依据 |
| 三个入口共享支付所有者，网关超时可能已扣款 | PASS：同一工程依据区块分别说明“共同所有者”“失败安全”“风险相称验证”三项独立影响 |

确定性检查另行覆盖 Skill frontmatter、核心注入体积、Hook 配置、构建和运行时测试；行为评测不以标题或方法名字符串匹配代替语义审查。

如果以后需要证明“哪些 reference 被读取”，那是**执行可观测性**问题，应从工具调用/trace 获取；最终回复的工程依据负责解释决定，不能替代运行轨迹。两者应保持分层。

## 八、最终推荐

对当前插件，最佳实践不是建立方法论使用日志、SQLite 或强制停止门禁，而是增加一个条件化的工程决策摘要：只显示一个区块，其中列出真正造成不同决定的多项方法，通常 1～3 项；没有实际影响时不显示。

> **展示决策影响，不展示方法名库存；提供可核查依据，不伪装成内部推理。**

它既满足用户对“这次到底用了什么、得出了什么结论”的可见性要求，又保持现有核心注入、按需 reference 和证据式交付的单一职责。
