# 面向 GPT-6 Astra 的指令精简方案

日期：2026-09-14。状态：保留原研究，并补充过度精简后的语义纠正。用户明确无需指定 Astra，已确认完整方法保留优先于长度目标；当前方案与进度由 [ADR-0004](../adr/0004-codex-first-bundled-engineering.md) 和[活动计划](../plans/2026-09-14-codex-first-refactor.md)持有。研究时内容变更尚未发布或更新到安装缓存，后续版本证据见 [v0.5.2 评测](../evals/v0.5.2.md)，研究本身不作为通过证据。

## 判断

推荐保留 GitHub 分发的自包含插件、生命周期注入和独立 Skill 入口，合并重复表达并缩短读取路径。原研究发现重复内容与评测口径问题，但没有证明可以删除用户明确要求的方法，也不足以证明整个分发架构有问题。Hook 送达成功不等于模型逐条落实。

初次实施把核心从 5,652 bytes 减到 3,694 bytes，细则从 35,943 bytes 减到 7,765 bytes，约减少 35% 和 78%。随后逐项审查发现常驻共同参与、功能核心与副作用外壳、组件原则、迁移差异、TDD 与特征测试等独有语义被削弱或遗漏。这是过度精简的中间稿，不是优化收益；方法名称仍留在维护文档不能替代运行时内容。用户据此确认恢复完整方法，保留三份主题细则与一级路由，具体映射见[方法治理](../methodologies.md#语义保留与改写映射)。

- **不是 Astra 实测**：上轮 8 回合实际为 `gpt-5.6-sol/high`；临时 `skills.config` 整数组覆盖只保留两项，未完整复现个人禁用配置。输入少 37.15%、未缓存输入少 14.46% 仅是该实验观察，不能外推 Astra、日常成本或 Hook 独立因果。[实验报告](/tmp/stoneplugins-ab.4pTBMb/report.md)、[运行脚本](/tmp/stoneplugins-ab.4pTBMb/run.mjs)
- **方案细节不足，不是已证实漏洞**：两侧 SIMPLE-1 都未明确非法输入处理及对应负测试；新版 TEST-1 正确保护 403，但未读旧规则要求的两份细则。结果质量与旧流程合规应分开评分。[实验报告](/tmp/stoneplugins-ab.4pTBMb/report.md)
- **读取统计漏标**：OWNER-1 新版循环读文件，汇总的 `read:false` 与 `fullOutput:true` 同时存在；仅识别 `commandActions.read` 会漏掉这种读取。不能把读取计数直接当行为分。[汇总](/tmp/stoneplugins-ab.4pTBMb/summary.json)
- **研究时的结构负担在内容层**：当时核心 5,652 bytes，五份细则合计 35,943 bytes；`method-selection.md` 又做一层路由，`architecture.md` 达 12,673 bytes 且重复核心原则，`decision-summary.md` 为每个实质决定增加格式读取。这是精简前快照，文件可在 [v0.5.1 Skill 树](https://github.com/sty20030818/StonePlugins/tree/v0.5.1/plugins/stoneplugins/skills/engineering)追溯，不代表候选当前大小。

上述 bytes 是文件大小，不是 token；临时实验文件可能被系统清理。研究时 [Hook](../../plugins/stoneplugins/src/inject-context.ts) 为 103 行，同包取源、无联网、超出 8,000 bytes 拒绝注入；当时新版四次核心均完整送达，没有重复读取核心。没有证据要求重写此层。

## 两篇主文带来的方向

[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)（2026-09-11）主张短且准确的描述、最小入口路由、只读当前任务需要的资料，重新检查旧模型留下的繁复步骤。对本项目，这支持合并重复表达和取消多跳读取，不能推出删除用户已确认的方法要求，也没有证明泛化措辞可以替代方法独有的动作、条件与退出要求。

[Model guidance：GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model)（查阅 2026-09-14，页面未标更新时间）说明 Astra 对冲突指令更敏感，也可能过度测试或过早询问。应写清已授权工作、完成条件和风险相称验证；不能把 API 示例当作覆盖用户 Git、发布或服务启动约定的新授权。

## 六篇补充一手资料

以下除单列发布日期的文章外，均为 2026-09-14 查阅的动态文档，页面未标更新时间。

1. [Build skills](https://learn.chatgpt.com/docs/build-skills)：先展示名称、描述和路径，选中后再读完整 Skill；描述可能因目录预算被截短。我们应前置准确触发条件，保持资源按需读取；不能推出“读 Markdown 不算用 Skill”或“必须增加 UI 调用次数”。
2. [Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)：全局与项目指令分层发现，近工作目录规则覆盖较早规则。个人偏好归全局、仓库事实归项目；不能因此把长期工程规则在多处手工复制。
3. [Best practices](https://learn.chatgpt.com/guides/best-practices)：优先短而准确的 AGENTS，重复出现实际错误后再补规则；Skill 聚焦真实工作流。适合删同义原则和无消费者流程，不代表越短越正确或安全底线可省略。
4. [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)（2026-01-22）：分开衡量结果、过程、风格和效率，先用少量明确检查及正反触发案例。文中 10 至 20 条 prompts 是起步建议，不是要求每次 60 回合，也不是 8 回合足以证明稳定收益。
5. [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：使用代表性场景、人工校准及成对比较，并警惕位置和长文偏见。应固定模型与环境、按真实结果评分；不能靠总分掩盖权限等关键失败。
6. [Hooks](https://learn.chatgpt.com/docs/hooks)：支持生命周期 `additionalContext`，根会话 compact 后可立即重新送达。它证明注入受支持，不证明强制正文注入或提示加载 Skill 哪个唯一最佳；提示送达也不是执行保证。

## 三种方案

| 方案 | 改动与收益 | 代价与边界 |
| --- | --- | --- |
| A：完整方法、合并表达、一级路由（修正后已批准） | 保留打包与核心注入，恢复方法独有语义，删重复表达、二级路由和机械格式必读 | 先核对语义保留再评路由与行为；仍承担核心常驻成本，不承诺固定降幅 |
| B：纯按需 Skill | 不再注入核心，普通聊天少带工程正文 | 重新依赖技能选择；只有放宽“工程核心常驻”目标时才优先 |
| C：只压缩措辞 | 不改路径，改动最小 | 可作过渡，但不解决触发过宽与多跳读取 |

这是基于本项目目标的推荐，不是官方指定架构。

## A 具体删什么、留什么

- **全局 AGENTS**：保留称呼、中文、授权、暂存边界、依赖提交约定、不主动启动服务；合并同义句，不把真实用户约束当旧模型补丁删除。
- **核心与 description**：缩短描述，前置工程任务范围，不扩大触发。正文保留完整常驻原则共同参与每项决定，包括整洁与六边形架构、单一职责、高内聚低耦合、组件化模块化、知识级 DRY、KISS、长期单轨及必要的破坏性推荐；输入、权限、失败、证据和授权要求继续保留，重复表达合并。
- **细则**：从核心按任务直达三份资源，取消“先读路由再选路由”；恢复各方法独有的判断、动作、反例和退出要求。条件控制具体结构和流程，不整体关闭原则，不以“只有一个实现”或“尚未发生问题”统一拒绝有当前价值的边界。相关方法可同时采用，不把全部细则拼回核心。
- **公开说明**：保留真实依据、决定与影响，取消通用固定前言与每次必读格式模板。保留用户确认的标题外置、引用、加粗后空格和独立的“影响与取舍”段，简短样式并入核心。
- **门禁**：精简前的 [validate-repository.ts](../../scripts/validate-repository.ts) 同时锁定方法名和格式短语；同步改为保护必要契约、路径和行为，删除关键词签到不降低安全检查。

研究阶段的表达示例，最终以候选文件为准：

> 对已授权任务，完成实现、必要检查及本次改动引起的修复。可自行决定范围内、可逆的实现细节；需要新增授权、发现用户修改冲突或不可恢复风险时暂停。检查通过后，仅在新增变化、失败或未解决风险出现时扩大或重复验证。

原有 Git 暂存、外部写入与发布、长期服务的授权边界照旧，示例不新增创建 PR 等权限。

## 怎样验证，不再先跑 60 次

用户已明确无需指定模型。先按语义映射核对原要求是否仍由运行时正文持有，再选择针对本次变化的正反案例。验证沿用当时默认模型，记录实际模型与推理强度，同批保持一致；四题、旧新各一次可作为 8 回合探索，不作为固定配额。完整保留其他 Skill 配置，仅改变被测指令，保持工具环境一致；实现案例使用可运行样例，既检查主动采用条件，也检查无价值结构和权限等负路径，有分歧才针对性复测。案例与扩样规则以[活动评测规范](../evals/behavior-cases.md)为准。

分开记录核心送达、实际产物/负测试、越权或额外改动、工具往返、输入/缓存/输出 token。涉及 Hook 改动再补生命周期验收；不以术语数量、引用块数量或“读了几篇”代表工程质量。本文不持有本轮通过结论，也不承诺精简后的节省比例。
