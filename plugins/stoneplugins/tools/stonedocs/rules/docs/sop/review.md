# 审阅目标或阶段并收尾

## 适用与读取

需要判断 Goal 或 Phase 的成果、记录复盘或按授权归档。先明确对象，读取对应 plan、阶段任务与验收、适用标准、受影响基线及遗留接收依据；共用规则见[共同约定](../conventions.md)。

## 操作

1. 区分只读判断、记录结论与实际归档；询问能否结束不自动授权改状态或归档。
2. 逐项核对原定成果、条件和适用结果。Phase 判断自己的贡献；Goal 判断选定阶段成果组合后的整体条件，引用阶段证据，只补缺口，不以阶段归档数量代替判断。
3. 缺少或失效的结果按 [verify](verify.md)处理。Goal 验收不等 Phase 先归档，Phase 退出不要求 Goal 已 done；验收/审阅 Task 以形成有依据的判断完成，不与对象状态互设前置。
4. 检查真正受影响的基线及遗留去向。结构没变不要求修改架构；非阻断遗留可按 [task](task.md)明确接收 Phase/Task 后收尾，阻断条件须完成或先确认范围调整，不能靠改名或移走规避。

   技术主题按[方法手册](../knowledge/technical-design.md)核对初始设计、当前实现和未来变更：已交付内容并入实际基线，未交付方案继续由明确设计或接收对象拥有；资料迁移按用户选择及主题唯一正文收敛。未来方案尚未全部实现本身不构成当前阶段阻断，也不能据此把初始设计写成已交付事实。
5. 先将判断、依据、偏差和遗留写入对应 plan 收尾节；有独立复盘价值才拆 review.md，plan 只保留入口。确认记录成立后，按各自条件更新审阅 Task，不循环重启流程。
6. 条件满足且已授权后，更新对应 Goal/Phase 的 done 与归档属性；取消按明确决定记录原因和去向。Goal 收尾须说明未结束工作的承接，不自动改写下属状态；Phase 归档后 Task 随之归档。
7. 核对状态、材料入口和接收位置一致。归档后新增工作由后续阶段承接，历史事实错误注明原因和依据更正，不悄悄恢复旧状态。

## 输出结构与示例

短结论放 plan 的收尾节，独立 review 使用相同内容：

```markdown
# <Goal 或 Phase 标识> 成果审阅

## 对象与依据
<实际审阅日期、对象计划版本、交付范围及适用验收批次。>

## 条件判断
- <原条件链接>：<成立、不成立或无法确认；引用实际依据>。

## 基线与偏差
<真正改变的当前规则、架构或指南位置；未改变则无需为收尾另写。
说明影响判断的偏差及值得保留的经验。>

## 遗留与接收
<每项遗留的影响、是否阻断、明确接收 Phase/Task；只记录本次处置，不复制后续状态。>

## 结论
<能否结束、适用限制、必要范围决定及实际授权；对象状态仍只在 plan 维护。>
```

## 完成判断

对象判断有依据，遗留有去向，实际写回符合授权。形成不通过的结论也可以完成审阅工作；归档、Git 提交和版本发布分别依其条件与授权处理。
