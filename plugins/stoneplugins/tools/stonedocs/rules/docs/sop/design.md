# 形成技术与实施设计

## 适用与读取

项目启动、整体技术/架构重审，或存在需要共同审查的结构、契约、关键流程和实施取舍时进入。读取产品方向与关键场景、已有资产及约束、相关 Phase plan（存在时）、行为标准、当前架构、决定及实际实现；共用规则见[共同约定](../conventions.md)，按问题读取[技术设计方法](../knowledge/technical-design.md)中组织、初始设计、任务就绪或迁移章节。

## 操作

1. 确认设计要满足的成果与约束，调查已有实现、原型资产、manifest/锁文件、实际入口与消费者。新项目或整体重审主动形成总体方案；已有架构与决定先核对适用性，复用有效部分，明确需要重审的范围，不预设全部保留或全部重写。
2. 按技术约定、系统架构、开发操作的职责推荐组织方式，说明复杂度依据，允许合并或拆专题。阶段变更围绕共同审查的方案组织 design.md；独立主题需要分开维护时用 designs/<topic>.md。多项 Task 可以共用一份设计，不按 Task 数量复制。
3. 按当前成果需要说明运行形态、目录与模块职责、输入输出和关键路径。新建或调整技术栈时，说明必要依赖、版本或发布通道、配置入口及选择理由；已有适用约定只引用，不为所有项目强制同一套架构。
4. 按实际影响展开数据所有权、权限边界、接口契约、事务与并发、失败处理、兼容、迁移及恢复；不涉及的内容无需为凑模板增设结构。
5. 解释选择与代价，重要长期取舍引用 decision，不维护第二份决定正文。涉及运行环境时，说明当前成果所需的最小可运行基线、环境前提和运行方式；按 [verify](verify.md)安排关键路径和失败路径的必要验证，不把计划写成实际成功。重排已有资料时先给现状、推荐、影响、内容保护与恢复范围，由用户选择保留、一次性重构或渐进迁移；按主题保持唯一正文，普通可逆细节不逐项重批。
6. 仅讨论、尚未确认或未获写回授权的部分先返回草案，不为使用 design 自动创建阶段或任务。无实现基线的新项目，初始技术设计已确认且获准保存时可写项目级技术/架构资料，并标明尚未实现的范围；已有原型仍保留其事实。已有系统的未来变化归草案或阶段，不覆盖当前说明。不影响当前成果的未来细节不阻断本次设计；实际交付按受影响主题同步当前规格/架构，未交付部分保留明确去向。

## 输出结构与示例

```markdown
# <方案主题> 实施设计

## 目标与约束
<目标和计划来源、已有架构/契约及本次范围。>

## 实施方案
<当前成果所需运行形态、目录与模块分工、输入输出和关键路径；按影响展开数据、权限、接口、事务并发、失败和兼容。>

## 选择与理由
<采用方案、必要依赖及版本/通道选择、真正影响选择的替代项、代价与确认依据；引用重要决定。>

## 影响与恢复
<受影响使用者、文件或数据；有迁移或覆盖时说明精确范围、恢复方式和限制。>

## 验证安排
<标准来源、关键风险、验证对象和方法；涉及运行环境时补可运行基线及必要前提，不预填实际成功。>

## 待决事项
<仍影响实施的选择或风险；无则删去。>
```

## 完成判断

当前待实施成果的关键选择明确，后续执行无需重新决定这些选择，影响当前成果的未决风险有去向。设计交付不等于实现完成，需要执行时按 [task](task.md)接续。

总体设计应足以解释技术选择、目录与模块、依赖、关键交互及开发验证入口；设计结束时说明完成的是总体/阶段设计还是实施安排，哪些任务输入已具备、哪些仍未细拆。不以文档数量或重复确认全部未来选择作为完成条件。
