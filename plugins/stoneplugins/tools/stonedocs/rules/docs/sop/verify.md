# 验收与复验交付

## 适用与读取

已有明确对象，需要验证 Task、Phase 或 Goal 的条件。读取完成条件、适用标准和差异、对象及已有结果；权限与证据原则见[共同约定](../conventions.md)。

## 操作

1. 明确本次要回答的问题、标准和覆盖范围。标准不足时说明缺口，不自行降低条件取得通过；Goal 验收重点检查组成成果的整体效果，复用适用的阶段结果。
2. 如实定位对象和标准版本，优先引用已有提交、构建或产物。正式取证前确认本批相关写入已结束，所用运行实例或产物对应受检文件。检查工作树时注明未提交状态、受检范围及影响；HEAD 不能代表未提交改动。结果不能无条件适用于后续变化。
3. 选择足以支持结论的材料。普通验收不自动创建 evidence 目录、完整日志、全量快照、清单、哈希或审计脚本。关键前后差异无法通过 Git 或已有产物恢复，且结论确实依赖它时，才保留必要原文或差异；行为实验优先使用可取回 base 加各次 diff 和实际观察定位样例，不为每例复制全套源码。不能复原的部分说明限制。
4. 在授权内执行必要检查，有效结果无相关变化时复用，只补缺失或失效部分。受检文件或运行产物变化时，只重建、复验受影响部分，无关工作可以继续并行。记录实际方法、观察和结论；命令检查注明退出码，静态、实际行为及外部运行分别说明。
5. 简单 Task 直接写所属条目的验证结果；阶段或目标的独立验收按下方结构追加到其 verification.md。结果只有一个正文所有者，其他位置只引用；附件确有需要才保存并链接。
6. 失败、未执行、未知分别记录，复验保留旧失败；标准变化注明版本和依据，记录错误更正说明原因。缺陷交给所属 Phase 的 Task，原 Phase 已归档则由后续阶段承接，不扩大本次实现授权。
7. 交付验收时，核对受影响的规格、架构及阶段未来差异与实现语义一致，已交付差异的并入位置可找到。核对实际记录和所用链接可找到、对象与标准匹配，不预引未来报告，也不为核对另做一份读回报告。验收 Task 可因取得真实结果而完成，被验收对象仍按自己的条件判断。

## 输出结构与示例

同一交付目标复用一个记录，复验追加批次。普通 Task 的简记使用相同必要信息，无需逐节建文件：

```markdown
# <Goal 或阶段交付目标> 验收记录

## 范围与标准
<要回答的问题、关联成果/Task、标准来源，以及本记录的覆盖边界。>

## <日期> · <本结果所有者内唯一批次>

- 对象版本：<实际提交、构建或工作树范围/状态；必要时链接最小差异>。
- 标准版本：<本批采用的规则、计划条件及可核对版本>。
- 方法：<实际操作或命令；只写影响结论的环境条件>。
- 实际结果：<逐条件的关键观察与通过、失败或未验证；命令含退出码>。
- 证据：<必要的已有产物、CI、日志或截图链接；关键输出可直接写入本条，无须另建附件>。
- 限制与后续：<未覆盖内容、结论适用边界、需处理的 Task 及后续复验>。
```

### CLI 原生批次

`result add` 复用上方字段；输入格式与示例以命令 help 为准。日期、对象版本、标准版本和实际结果显式提供，不能用当前时间或 HEAD 代替未提交改动的实际范围。没有附件或补充限制时分别明确传空数组；结果可以失败或未验证，记录本身不改变任何对象状态。已有独立报告可直接作为完成依据，不要求补演 `result add`。

Task 的结果正文只写在自己的唯一条目内；Goal 和 Phase 写在自己的 `verification.md`，首批需要时才创建。CLI 用带 `v1` 的 `stonedocs:result` 起止注释标识批次，稳定 anchor 包含对象类型、标识和批次，例如 `result-task-t0001-http-1`。批次在该结果所有者内唯一，因此不同 Task 可以使用相同批次名。文字字段使用足够长的 Markdown 围栏，字段中的标题、状态或示例不能成为真实任务；证据保留为项目内可定位链接，不另存整份 JSON 或摘要副本。

同所有者、同批次、同完整内容重试不写入；异内容、重复或无法识别的原生块报冲突，新复验使用新批次并保留旧失败。首次写 Task 只将工具的“尚未执行。”占位换成批次入口，已有真实简记原样保留。`result show` 只读，返回原文、可识别批次及未结构化或损坏格式提示；历史自由格式内容不能被解释成“没有结果”。已完成但未归档的对象可追加复验，自己或祖先归档后的普通新增拒绝。

## 完成判断

结果与实际对象、原定条件相符，足以支持此次结论，局限已说明。未取得结果、只存在骨架或检查计划时，不能写为验收通过。
