# 文档共同约定

本文件拥有共用模型、文档职责、标识、状态、权限与版本规则。具体流程、输出骨架和完成判断由对应 [SOP](sop/README.md)维护；采用项目的指南提供使用路线，不另定义规则。

## 基本模型

- 产品目标（Goal）表达一组希望达成的用户成果，明确由哪些阶段共同交付，并独立验收。V1 等目标标识不等于发布版本号。
- 成果阶段（Phase）属于一个目标，拥有自己的计划和一份任务清单；不同阶段可以按依赖并行。
- 任务（Task）始终属于一个阶段，按可验收成果拆分，可以单独推进、验证和交接。任务、故事、Git 提交和发布之间不要求一一对应。
- 完整规划层级是 Goal → Phase → Task。Phase 内的清单分组和 Task 内的实施步骤不新增工作对象，不另设生命周期、退出条件或状态。
- 每种事实只有一个可独立修改的所有者。允许引用、带来源摘要和标明时点的历史记录，不维护第二份活跃规则或任务状态。
- 使用 Markdown + Git；文档按真实内容创建。技能、CLI 或外部平台是可选入口，手工路径始终可用。

## 文档职责

路径采用英文小写，正文默认中文。根级约定文件保留 `README.md`、`AGENTS.md`、`CONTEXT.md`。

| 路径 | 唯一负责的内容 | 更新时机 |
| --- | --- | --- |
| `README.md` | 项目是什么、如何开始使用、必要入口 | 产品说明或使用入口变化 |
| `AGENTS.md` | 本项目约束、适用 SOP、读取路线和写回入口 | 协作约束或入口变化 |
| `docs/README.md` | 按目的组织的阅读路线、文件位置及当前/历史资料区别 | 导航变化 |
| `docs/conventions.md` | 跨流程共用约定 | 共用规则改变 |
| `docs/sop/README.md` | 流程选择与衔接导航 | 流程入口改变 |
| `docs/sop/<workflow>.md` | 单个流程的适用条件、读取、操作、输出骨架和完成判断 | 该流程改变 |
| `docs/product.md` | PRD：用户、问题、产品价值、范围、成功标准和持久取舍 | 产品方向改变 |
| `docs/roadmap.md` | 跨目标优先级、推进主线、依赖和目标入口 | 整体安排改变 |
| `docs/goals/<goal>/plan.md` | 该目标的成果、范围、组成 Phase、整体条件、状态和收尾入口 | 目标规划、组成或结论改变 |
| 同目标 `verification.md` | 目标整体验收的各次实际结果 | 整体条件取得新结果 |
| 同目标 `phases/<id>-<outcome>/plan.md` | 该阶段的背景、成果/故事、范围、退出条件、依赖、推进思路和状态 | 阶段规划、范围或结论改变 |
| 同阶段 `tasks.md` | 本阶段 Task 的身份、状态、交付物、完成条件、材料、实际结果和接续点 | 拆分、开工、阻塞、完成或交接 |
| 同阶段 `design.md` / `designs/<topic>.md` | 需要共同审查的结构、契约、关键流程、实施取舍和验证安排 | 存在独立审查需要 |
| 同阶段 `spec-deltas.md` 或 plan 中的目标差异节 | 相对当前基线的未来行为变化及确认依据 | 行为变化确认，交付时注明并入位置 |
| 同阶段 `verification.md` | 阶段交付目标的各次验证、对象版本、方法、实际结果及限制 | 需要批次记录或独立验收时 |
| 目标或阶段 `review.md`，或对应 plan 的收尾节 | 本次成果判断、偏差、经验及遗留去向 | 审阅收尾时；内容有独立价值才拆文件 |
| `docs/specs/<capability>.md` | 当前已交付行为：能力边界、业务规则、代表场景和质量约束 | 行为交付时同步 |
| `docs/architecture.md` | 当前系统边界、模块责任、数据所有权、交互、契约及重要决定入口 | 已交付的结构或契约改变 |
| `docs/decisions/<id>-<topic>.md` | 重要长期取舍的背景、选项、选择、理由、代价和替代关系 | 存在长期需要解释的决定 |
| `docs/research/<question>.md` 或阶段内 `research/` | 同一问题的来源、假设、方法、观察、推荐和局限 | 不确定性需要调查 |
| `docs/guide.md` | 使用路线、请求示例和跨流程接续 | 操作说明需要调整 |
| `CONTEXT.md` | 领域及项目特有概念、别名和易混区别 | 术语影响理解时 |
| `docs/ideas.md` | 尚未承诺实施的想法、价值和待讨论问题 | 记录、采纳、放弃或实现时 |
| `docs/releases.md` | 实际发布的版本、范围、产物、适用证据和已知限制 | 确有发布时追加 |

目标的组成阶段只在目标 plan 中维护，roadmap 不重复阶段名单或状态。阶段计划引用所属目标，任务归属由所在阶段的 tasks.md 确定，不另建目标级或阶段外任务清单。

架构不记录本机安装环境、版本发布进度、验收统计或某次迁移经过。这些事实分别进入对应任务、验收、收尾或发布记录；仅因阶段结束或插件发布，不更新架构。

`spec` 表达行为，`design` 表达实现方式，plan 表达成果和推进。行为标准只维护一份，目标、阶段和发布引用它并记录各自实际结果。骨架和示例随对应 SOP 维护，不另建模板事实源；示例编号和占位文本必须按实际替换。

## 标识与状态

目标使用 V1 等稳定标识，目录例如 `v1`。Phase 使用项目内唯一的 `P001`，目录例如 `p001-workflow-foundation`；Task 使用项目内唯一的 `T0001`，编号不依赖所属阶段。创建前检索编号，并行新增由协调者分配。标题可改，已引用身份保持含义；重组位置时同步修正引用，不保留两套活跃记录。

Goal、Phase 的 plan 仅需 YAML `id`、`status`，归档时增加 `archived: true`。Task 状态只写在所属 tasks.md 的唯一条目。导航、目标组成表、主题分组和验收记录不复制当前状态；其他文档不普遍要求状态、负责人或更新时间。

三类对象共同使用：

- `todo`：已纳入计划，尚未开展。
- `doing`：正在推进；阻塞时仍保持此状态，记录原因和接续条件。
- `done`：约定成果及必要验证已完成，有可定位依据。
- `cancelled`：明确决定不再继续，记录依据、影响和遗留去向。

归档是独立属性，只用于已 done 或 cancelled 的 Goal、Phase。Task 随所属 Phase 归档，不另设任务归档字段。目标状态不由任务数量或阶段归档数量自动计算，目标归档也不自动改写下属状态；仍未结束的工作须先明确承接去向。

## 读取、授权与写回

先区分讨论、只读审查与执行写回；已有授权覆盖的工作继续推进，不因切换流程另造审批。涉及产品方向、关键架构、承诺范围、退出条件或外部写入的新影响时，按项目约定取得确认。

开始读项目 AGENTS 和适用 SOP。新方向从 PRD、roadmap、目标 plan 进入；已有任务直接定位阶段 plan/tasks，再按关联读标准、设计、决定和结果，不要求通读全仓。

确认决定、开工、取得重要结果、阻塞、交接和收工时，更新对应事实所有者及受影响引用。写前读最新文件，多个执行者明确文件责任。既检查内容真实，也检查该文件是否拥有这些内容；链接、格式或 Git 合并通过不证明语义正确。

新增 Task 须能说明支撑本阶段哪个已确认成果。小修由支撑其目标的当前阶段承接；新增独立价值或改变退出条件时先讨论范围，尚未承诺的内容留在 ideas。阶段已归档后，新工作由后续承接阶段管理，不悄悄重开；不因每次修复、提交或发布自动创建阶段。

## 流程独立与组合

每项流程可以单独进入，不要求调用过前序技能。所需事实可来自现有文档、用户明确输入或实际实现；读取清单不是必须补建文件的清单。输入不足先调查可发现的事实，只澄清影响结果的缺口，未决选择不写成确认。

流程通过内容和链接交接，不通过调用记录交接。同一执行者可在授权内连续承担多项职责，无需循环调用技能更新状态。plan/review 须明确处理的是 Goal 还是 Phase；task 只能处理实际所属 Phase 的任务。独立使用不等于独立复制一个技能目录就包含全部运行资源。

插件是否可用以实际安装环境为准。项目采用的规则版本不会随插件升级自动改变；版本或项目差异影响本次读写时，说明冲突并暂停受影响写入。无技能、CLI 时仍可按 SOP 使用普通文件和 Git。

## 当前基线与未来差异

当前规格拥有已交付行为，阶段保留未来差异和确认依据。交付时将实现、必要验证及真正受影响的规格、架构或指南组成同组可审查结果；差异注明并入位置后成为历史引用。结构未变化则不更新架构。

多阶段影响同一规则时明确写入责任，基线变化后核对未交付差异。事实、决定、假设、建议和待决项分开表达；不能把缺陷改写成标准，也不能以最后修改时间任选事实源。

## 完成与证据

完成判断由原定条件和实际结果支持。普通 Task 可在条目中简记对象版本、方法、结果及必要链接；需要批次或独立判断时写对应 verification.md。证据应足以支持结论，材料多少不代表验证充分。

Goal 验收检查阶段成果组合后的整体条件，引用可用的阶段结果，只补组合风险和证据缺口；不要求 Phase 先归档。Phase 退出不依赖 Goal 已 done。承担整体验收的 Task 仍属于某个 Phase，其完成条件可为取得实际结果并形成判断；报告进入 Goal 的 verification.md，不能把 Goal 通过作为该验收 Task 的循环前置。

静态检查、实际行为与外部运行分别说明；未执行、失败、未知不能写成通过。复验保留旧失败，错误更正注明依据；验证或审阅工作形成了有依据的判断，不代表被检查对象已经达成目标。具体操作和最小记录见 [verify](sop/verify.md)。

完成后按 [review](sop/review.md)处理结论、遗留和归档，保留原路径。历史资料按当时对象及标准解释，事实更正说明原因和依据；重组当前结构不重写历史验证结论。

## 目标与发布

目标、阶段、提交、tag 和实际发布是不同事实。阶段与 release 多对多，V1 等产品目标不自动承诺某个 SemVer 版本。发布范围和使用门槛由项目自己决定。

发布意图简记在承接其范围的一个目标或阶段 plan 中，不复制任务，也不另造一套发布计划体系。实际发布再追加 releases，引用已有条件和结果；产物出现新的集成风险时补相应验证。发布仍依具体授权执行。

发布意图的最小内容是显式版本、选入成果引用和放行条件；一个承接 plan 可以规划多个版本，同版只在一处维护。实际记录的最小内容是版本、明确实际日期、实际范围、产物引用、适用证据和已知限制；它可独立于先前计划补记，引用已归档成果不要求重开计划。失败或未确认发生的发布仍留在执行任务/验收，不登记为实际发布。

原生发布块使用版本化边界和稳定入口，计划与实际记录各自同版同内容重试无变化，不同内容先明确更正，不覆盖历史。自由格式保留，未知格式不能被当作不存在。项目引用须可定位，外部链接只保存适合公开分享的地址；记录工具校验结构与引用，不代替执行者确认发布真实发生，也不自动推进阶段、目标或归档。

## 规则改进与分发

从实际问题判断应修改实例、某个 SOP、指南还是共同约定，更新受影响消费者，再验证暴露问题的场景。一次成功不证明所有环境或长期可靠性；研究和建议不直接覆盖当前规则。

规范作者源、技能源码与采用项目各自拥有自己的内容。技能包若分发固定规则副本，应注明来源版本并校验一致，运行资源随包提供，不能依赖作者电脑路径或远端 latest。这是分发契约，不要求每项普通任务另建来源包、哈希清单或审计脚本。

机器采用记录 `docs/.stonedocs.json` 只拥有规范的固定来源、格式/规则契约与管理范围，AGENTS 引用它并维护项目例外；不存任务状态、完成率或本机工具版本。规则包完整性、本地差异以及某个动作的适用性分别判断，采用或插件更新不自动覆盖项目差异。

CLI、hook 和外部任务平台不隐式改变任务状态所有权。需要改变来源或增加同步时，先明确权限、冲突、失败和恢复约定，再按授权实验。
