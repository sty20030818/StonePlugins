# 项目技术设计与自适应文档方法

## 适用范围与规则关系

本手册面向项目启动、整体架构重审、阶段设计和已有项目资料迁移，解释怎样调查、比较和组织技术资料。核心原则是关键内容必须覆盖，文件组织按项目复杂度调整。

本篇随规则契约 2 的共同约定与 SOP 作为同源有效方法使用，本文无需聊天上下文即可阅读。作者集合生效、固定构建、正式发布、插件安装与项目采用是不同事实；本仓作者修改不自动升级既有项目。旧 v1 项目继续按其本地规则，只有明确采用或升级后才使用匹配的 v2 方法；项目例外与授权仍须核对。

共用规则见[共同约定](../conventions.md)，操作与完成判断见对应 [SOP](../sop/README.md)；本手册拥有具体方法、选项与例子，不另维护同一规则正文。必需方法缺失、损坏或来源不明时，只暂停依赖它的设计/写回，继续无关只读调查，不从作者 checkout、插件缓存或远端 latest 静默补入并冒称本地规则。调查依据和本仓实施安排从资料导航进入，手册执行不依赖作者研发目录。

## 已确认的方法方向

1. 新项目和整体重审先讨论总体技术方案；阶段细拆实施任务前核对相关设计。
2. 技术、架构和开发操作职责分清，文件数量与组织方式按项目复杂度调整。
3. 借鉴 VS Code，为 AI 提供目录地图、模块边界、工作约束和验证入口。
4. 新项目可以先保存已确认、尚未实现的初始技术设计，明确与实际实现的区别；后续变更通过阶段设计接续。
5. 已有项目允许重排。AI 先展示改进方案、理由、影响和恢复方式，用户选择是否采用，以及保留、一次性重构或渐进迁移。
6. 每项事实只有一个有效正文所有者，其他位置通过链接或带来源摘要复用。
7. AI 负责调查和给出推荐，用户确认方向、关键取舍和不可接受的成本；普通可逆细节按项目约定判断，已明确的授权不重复确认。

## 自适应文档组织

### 判断依据

由 AI 根据项目事实提出组织方式和理由，用户可以调整，不要求用户先自行判断“小、中、大”。主要考察：

1. 运行形态：单个程序，还是前后端、多端、多服务。
2. 模块关系：职责是否独立，是否有跨模块契约。
3. 数据风险：是否涉及账号、持久化、离线同步、迁移和恢复。
4. 协作方式：是否需要跨会话、多人或多个 Agent 接续。

代码行数、目录数量和文件数量不能单独决定文档深度。代码不多的同步应用，也可能比大型静态网站更需要设计说明。

| 项目情况 | 默认组织方式 | 进一步拆分的依据 |
| --- | --- | --- |
| 简单工具、单一应用 | README 或简短技术文档集中说明技术、结构和开发方法；AGENTS 提供约束和入口 | 内容已有独立阅读、维护或审查需要 |
| 持续迭代的多模块应用 | 技术与工程约定、系统架构、开发指南分别维护；变更设计归所属阶段 | 某个模块或协议无法在总体说明中讲清 |
| 多端、多服务、复杂协作项目 | 总体文档提供地图；重要模块、协议、部署和恢复机制按需展开 | 子系统有独立契约、生命周期或维护责任 |

这是资料组织建议，不增加 Goal → Phase → Task 之外的工作层级，也不增加“小项目状态”或“大项目类型”等机器对象。

### 拆合时机与边界

启动、整体重审和阶段设计核对时重新评估组织方式；日常小修改沿用现有安排。出现以下情况时考虑拆分：

- 一份文档反复混入技术约定、架构解释和操作步骤。
- 模块具有独立的协议、状态机或恢复机制，总览不足以解释。
- 不同执行者反复修改同一长文，或多处复制同一规则。
- AI 经常找错代码位置、违反依赖方向，或需要靠聊天补充关键背景。

长期只有几句话、没有独立维护价值的文件可以合并。用户可以选择其他组织方式，关键内容仍须覆盖。

小项目不能省略它实际涉及的数据、安全和恢复问题。项目变大也不自动要求拆包、微服务或增加架构层；文档描述真实设计，不制造产品复杂度。

### 三种真实选项

| 方案 | 文档组成 | 适用范围与取舍 |
| --- | --- | --- |
| A：两份技术文档 | 技术说明与系统架构；开发操作放技术说明 | 适合工具和运行方式简单的小项目，文件少，但增长后可能需要拆分 |
| B：两份技术主文档与独立开发指南 | 技术与工程约定、系统架构、开发指南 | 默认推荐，适合持续迭代的多模块项目，阅读目的和更新原因较清楚 |
| C：分层展开 | B 提供总入口，复杂模块、协议和部署另设专题 | 适合复杂系统，按实际内容增加，不给每个目录强制配文档 |

## 文档职责与默认内容

文件名是默认建议。已有项目可复用职责相同的现有文件，小项目可合并章节，复杂项目可拆出独立专题。

| 文档 | 唯一负责的内容 |
| --- | --- |
| `docs/technology.md` | 技术选型、工具链与项目工程约定 |
| `docs/architecture.md` | 系统结构、模块职责、依赖、主要目录、数据所有权和关键交互 |
| `docs/development.md` | 环境准备、配置入口、开发、检查、测试和调试方法 |
| 阶段 `design.md` / `designs/` | 本次交付如何改变系统，以及影响、风险和验证安排 |
| `docs/decisions/` | 重要长期选择的背景、替代方案、理由与代价 |
| `AGENTS.md` | AI 必须遵循的约束、简短项目地图和按问题读取的入口 |
| `docs/README.md` | 文档导航，区分当前事实、待实施设计和历史资料 |
| `CONTEXT.md` | 领域术语与易混概念 |

### 技术与工程约定

应按项目需要包含：

- 语言、运行时、框架、关键依赖及用途。
- 选型理由、实际约束和重要替代项。
- 包管理、构建、格式、类型检查与测试工具的分工。
- 项目特有的命名、错误处理、异步和资源管理约定。
- 测试策略，以及交付所需的必要检查。

精确版本引用 manifest、锁文件和工具链配置，不另维护容易过期的实时版本清单。重要选型理由较长时引用 decision。普通通用建议没有必要重复抄写，项目差异和真实约束应明确。

### 系统架构

应按项目需要包含：

- 系统边界、运行端和外部依赖。
- 模块职责、公开能力、不承担的责任。
- 依赖方向及需要持续保护的约束。
- 主要代码目录与模块的对应关系。
- 关键数据所有权、读写路径和协作流程。
- 信任边界，以及相关失败、重试、事务和恢复责任。
- 复杂专题和重要决定的入口。

带职责说明的主要目录树归这里。技术文档可以提供顶层工具入口或链接，不重复维护完整目录树。质量要求由适用规格或阶段条件拥有，架构说明满足这些要求的方式。

总体图解释系统边界与运行单元，模块图解释重要依赖，关键流程说明实际协作。按阅读价值选择图示，不要求每个项目画齐全部层次。

### 开发指南

应按项目需要包含：

- 必要环境和工具前提。
- 配置文件、配置项及安全示例的入口，不记录真实凭据。
- 初始化、普通启动和数据维护的区别。
- 仓库实际支持的检查、测试、构建与调试命令。
- 常见故障的判断与恢复方法。

开发指南维护可重复的操作方法，某次执行结果进入任务或验收，不写成长期操作正文。

### 三份资料如何配合

以存储模块为例：

- 架构写它负责哪些事务和持久化责任、与其他模块如何协作、代码在哪里。
- 开发指南写怎样准备和运行本地数据库。
- 技术约定写选择这类存储技术的原因、工具约束和相应工程规则。

各自引用，不重复解释整套机制。类型、schema、精确字段和命令配置已有源码所有者时，文档解释语义、边界和理由，不复制第二份可独立修改的实现真相。

## 初始设计、当前实现与未来变更

### 资料性质

| 情况 | 建议记录方式 |
| --- | --- |
| 尚在讨论，关键选择未确认 | 保留为草案或研究推荐，明确未决项 |
| 新项目没有实现基线，初始技术方案已确认且获准写回 | 项目级技术与架构文档可以承载初始设计，显式说明尚未实现的范围 |
| 项目已有实现 | 当前架构描述实际结构，拟进行的改变进入阶段设计 |
| 部分设计实际交付 | 更新已落地技术主题；未交付部分继续由明确的未来设计拥有 |
| 设计被替代 | 当前正文采用有效结论，重要替代关系由 decision 或相关设计保留 |

### 初始设计的适用边界

- 尚未建立 Phase 时，可以形成已确认且获准写回的项目级初始技术资料，不为存放设计强行建立阶段。
- Task 仍须属于明确 Phase，讨论或方案保存不产生阶段外任务。
- “作为新项目重新开始”不自动抹去现有原型事实。原型资产须先盘点，再明确保留、替换和退出范围。
- 初始设计不能冒充已安装依赖、已实现结构、已通过验证或已上线行为。
- 不将初始技术设计例外扩展成覆盖已有当前规格或历史验收的理由。

### 部分交付后的收敛

以实际交付内容逐项核对：已落地部分成为当前说明；尚未落地的具体方案转入或继续由相应阶段设计拥有，总体文档保留入口。重要长期决定可继续由 decision 解释，但不维护两份完整的方案正文。

不要求每提交一个文件就重写整篇架构，也不能一直把完整目标方案标为当前实现。同步对象是本次实际改变的技术主题。

结构已实现、行为已验收、已经上线分别陈述，证据各自成立。不新增通用文档机器状态或审批对象，需要时以简短说明表达资料性质与适用范围，继续使用现有 Goal/Phase/Task 生命周期。

## 从总体设计衔接到任务

### 新项目路线

```text
明确产品方向与关键场景
    ↓
粗排目标、阶段和主要依赖
    ↓
讨论并确认总体技术方案
    ↓
核对当前阶段需要的具体设计
    ↓
细拆实施任务
    ↓
实现、验证并同步受影响文档
```

这是资料和问题的衔接路线，不是技能调用顺序。已有内容足够时直接复用，不补演上游调用历史。

总体设计决定系统组成与长期约束；阶段设计说明本次成果如何实现，或者为何需要改变总体结构。普通文件和函数如何编排，通常由执行者按约定判断，不要求提前逐个确认。

### 细拆实施任务前的就绪检查

1. 当前成果和边界明确。
2. 适用总体架构与技术约定能够找到。
3. 会改变模块、契约或任务依赖的选择已经确认。
4. 相关数据、权限、失败和恢复责任明确。
5. 验证方式足以判断成果是否完成。
6. 剩余未知有明确影响范围和处理方式。

不能满足时，只暂停依赖相关未知的实施安排。确认依据可来自已有文档、真实讨论和实际实现，不增加一套独立审批记录。

### 允许先行的工作

- 目标和阶段可以先粗排。
- 必要调查和可行性实验可以先安排，仍使用所属阶段的普通 Task。
- 调查任务以证据和可审查结论交付，不能将产品能力实现写为已完成。
- 不相关的未来选择不阻断当前已有依据的交付。
- 已确认且仍适用的方案不重复审定。
- 普通可逆细节按项目约定判断，不要求每项任务重新做总体设计。

例如，存储方案尚未确定，且会改变接口、部署和模块职责时，先调查或实验；尚未选择未来移动平台，则通常不应阻断当前已明确的 Web 成果。

设计结束时自然说明当前完成的是总体设计、阶段设计还是实施安排，以及哪些任务具备输入、哪些尚未细拆；不把设计完成说成产品实现完成。

## 已有项目采用与迁移选择

### 选择前提供的内容

AI 先给出可审查方案，再由用户选择是否采用和迁移方式。方案应包含：

- 当前结构及具体的重复、缺口、冲突或阅读困难。
- 推荐结构、适用理由和保留现状的真实替代项。
- 文件与主题的移动、拆分、合并关系。
- 受影响的链接、指令、脚本和工具消费者。
- 必须保留的决定、未决问题和历史证据。
- 恢复方式与不能完全恢复的限制。

| 选项 | 执行方式 | 需要明确的条件 |
| --- | --- | --- |
| 保留现有结构 | 原位补缺口、明确职责与导航 | 用户知道仍保留哪些结构限制 |
| 一次性重构 | 同批重排正文、修正引用并退出旧位置 | 精确范围、消费者影响和恢复依据清楚 |
| 渐进迁移 | 按主题或模块逐步切换正文所有权 | 每一步范围、当前权威位置和退出条件清楚 |

AI 给出推荐与理由，用户选择是否采用及迁移方式。明确选择并授权后按范围执行；发现未知关键消费者、内容冲突或新增不可恢复影响时再暂停说明。

### 渐进迁移的单一事实源

按主题切换所有权，不同时维护新旧两套完整文档：

1. 盘点主题和当前权威位置，尚未迁移的正文继续保留。
2. 每次只迁移选定主题，并同批更新导航和实际引用。
3. 已迁主题的旧位置退出活跃正文，必要时保留明确的历史说明或指向；这类过渡指向应有保留理由和清理条件。
4. 其他未迁主题继续由旧位置拥有，新文件存在不表示整体迁移已经完成。
5. 迁移完成后退出不再需要的过渡指向，不留下永久双轨。

例如，架构主题已迁到新文件，而开发操作尚未迁移，就分别从新架构和旧操作位置读取，不在两边各维护完整技术正文。

### 内容保护与恢复

文档重排不等于删除事实。已确认规则、真实未决问题、旧失败和验收适用边界均需保留。

Git 已有历史可以引用；未提交且将被覆盖的原文，需要保留必要差异或恢复材料，不能假定 Git 能恢复。保留用户 staged/unstaged 分界，不用暂存、stash 或还原来方便迁移，不默认生成全量备份包或独立迁移台账。

### 可自适应资料与工具契约

项目技术资料可以按需要组织。CLI 定位的 Goal/Phase/Task 位置、固定规则路径和采用片段则有机器消费者。用户希望连这些约定一起重排时，应一并展示兼容改造和迁移成本。

本次推荐保持工具契约，先完善技术资料与流程；不能把“允许用户重排”解释为任意改名后现有 CLI 仍会自然支持。

## AI 入口与技能接续

### 能工作的工程地图

借鉴 VS Code，AGENTS 提供简短但足够工作的地图：

- 项目主要组成。
- 不可忽略的依赖、数据和权限约束。
- 按当前问题读取资料的路线。
- 必要验证命令和交付要求。
- 当前授权和写回边界。

详细架构、协议和工程规则通过链接进入。复杂模块有独立约束时可以增加就近入口，并在总入口说明适用范围。入口摘要标明来源，不复制完整技术正文；不为不同 AI 工具维护多份可独立修改的完整规则。

| 当前工作 | 应读取的技术资料 |
| --- | --- |
| 新项目启动 | 产品方向、已有约束与资产盘点，再形成技术和架构方案 |
| 整体重审 | 当前结构、原型资产、关键契约、相关决定与替换约束 |
| 阶段规划、细拆任务 | 适用总体方案、本阶段变化、关键未决项与验证安排 |
| 普通任务接续 | 所属阶段、唯一任务及直接相关的技术材料 |
| 验收与收尾 | 实际交付对象、受影响技术主题、设计并入位置与剩余限制 |


## 方法取舍

### 按职责组织，按复杂度决定文件

桌面项目既有长文混杂，也有多份文档重复同一机制。单一职责、单一事实源与 KISS 用于确定内容所有者，再允许合并或拆分。

影响与取舍：维护位置更清楚，但执行者需要解释组织依据，不能只按项目规模套目录。没有独立维护价值时合并，有真实复杂度时展开。


### 关键设计约束实际任务安排

会改变模块、契约与依赖的未决选择会直接影响任务边界。先取得事实并确认相关选择，再细拆实施任务；调查任务用于解决事实缺口。

影响与取舍：前期增加必要设计，同时保留已有方案复用、普通小改和探索任务的直接通路，避免总体设计变成无限前置工作。


### 保持设计与事实可区分

初始项目需要先讨论整体技术方向，已有项目又需要可信的当前说明。明确初始设计例外及交付后收敛方式，避免把目标方案写成已经实现的事实。

影响与取舍：部分交付时需要按主题同步资料和未来设计入口；不能只改一个文件标题就宣称全部方案已落地。


### 迁移选择由用户决定

结构改进与切换成本应同时进入选择。先提供目标结构、范围、消费者影响和恢复方式，再由用户选择是否采用及迁移方式。

影响与取舍：允许清理旧结构，也允许保留有效组织；渐进迁移仍必须收敛到每项事实一个正文所有者，不能成为永久双轨的理由。
