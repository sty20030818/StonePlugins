# 文档共同约定

本文件拥有各流程共用的文档模型、内容所有权、标识、状态、权限与版本规则。具体操作、对应产物的填写骨架与完成判断由各自 [SOP](sop/README.md)统一维护。采用项目的目标、任务和证据在自己的资料中维护。

## 基本模型

- 产品目标解释为什么做。阶段按成果组织，可以并行，每阶段拥有一份任务清单。
- 任务以可验收结果拆分，与提交数量无关。一项任务可以服务多个用户故事，一个故事也可以由多个任务完成。
- release 与阶段多对多。一阶段可提供多个 beta 或正式版本，一次发布也可汇集多个阶段的成果。
- 当前规格拥有已交付基线的行为规则，阶段保留未来差异。实际结果由验收证据说明，契约存在不代表每次执行都成功。
- 每种事实只有一个可独立修改的所有者。允许引用、带来源摘要和标明时点的历史记录，不维护第二份活跃规则或任务状态。
- 初始使用 Markdown + Git。工作流可以从任一适用步骤进入，文档按真实内容创建。

## 文档职责

采用浅层职责目录、英文小写路径、中文正文。根级约定文件保留 `README.md`、`AGENTS.md`、`CONTEXT.md`。

| 路径 | 内容所有权 | 创建与更新时机 |
| --- | --- | --- |
| `README.md` | 项目是什么、如何开始使用、必要入口 | 项目建立、可使用内容或使用入口变化 |
| `AGENTS.md` | 本项目约束、适用 SOP、开始与恢复读取路线、任务和事实写回入口 | AI 协作开始、入口或项目约束变化 |
| `docs/README.md` | 按目的组织的阅读路线、文档位置及当前/历史资料的区别 | 文档需要导航、文件职责或位置变化 |
| `docs/conventions.md` | 文档模型、所有权、标识、状态、权限和版本等共用规则 | 跨流程约定确认或改变 |
| `docs/sop/<workflow>.md` | 单个流程的适用条件、读取、操作、输出结构与完成判断 | 独立流程确认或优化 |
| `docs/sop/README.md` | 流程选择与衔接入口 | 流程入口或职责改变 |
| `docs/product.md` | PRD，目标用户、问题、产品目标与价值、范围与非目标、成功标准、持久取舍 | 产品方向确认或改变 |
| `docs/roadmap.md` | 产品目标关联、整体优先级、推进主线、阶段成果与 plan 入口、依赖及跨阶段发布意图 | 规划阶段、优先级或关系改变 |
| `docs/specs/<capability>.md` | 能力边界、当前规则、正常/失败/边界场景、质量约束与相关来源 | 能力交付时与实现同步更新 |
| `docs/architecture.md` | 当前系统边界、模块责任、数据所有权、交互、约束和重要决定入口 | 当前架构随交付改变 |
| `docs/decisions/<id>-<topic>.md` | 重要产品或技术决定的背景、真实选项、选择、理由、代价、替代关系 | 存在长期需要解释的取舍 |
| `docs/phases/<id>-<outcome>/plan.md` | 背景、成果与故事、范围、退出条件、依赖、推进思路、风险、材料入口和收尾 | 阶段开始规划，范围或结论改变 |
| 同阶段 `design.md` / `designs/<topic>.md` | 需要一起审查的设计，结构、数据/契约、流程、失败、兼容/迁移、实现与验证方式 | 存在独立审查的技术方案，多任务可共用 |
| 同阶段 `tasks.md` | 本阶段任务的身份、状态、完成条件、依赖和证据 | 拆分、开工、阻塞、完成、交接时 |
| 同阶段 `spec-deltas.md` 或计划内差异节 | 相对哪个当前基线新增/修改/删除什么规则和场景、确认依据 | 新行为讨论确定，交付时转为历史引用 |
| 同阶段 `verification/<target>.md` | 某交付目标的各次验证，对象与标准版本、方法环境、实际结果、证据和限制 | 每次取得相关验证结果时追加 |
| 同阶段 `review.md` 或计划收尾节 | 成果结论、偏差、重要经验和遗留去向 | 阶段 review，内容有独立价值时拆文件 |
| `docs/research/<question>.md` / 阶段内 `research/` | 同一问题的调研与实验，问题、来源、假设、方法、观察、结论及局限 | 不确定性需要证据，结论不自动成为决定 |
| `docs/guide.md` | 使用路线、自然语言请求示例、跨流程衔接及规则入口 | 有可执行操作需要说明时 |
| `CONTEXT.md` | 领域及项目特有技术概念、含义、别名、易混区别、必要来源与详细资料入口 | 出现会影响理解的术语 |
| `docs/ideas.md` | 尚未安排的想法、价值、必要背景和待讨论问题 | 随手记录，采纳/放弃/实现后明确去向并移出待处理区 |
| `docs/releases.md` | 实际发生的版本、交付范围、产物、适用证据和已知限制 | 确有发布时追加 |

计划包含必要的技术概述，详细实现由 design 承担。`spec` 表达可观察行为，`design` 表达怎么实现。行为验收标准在一个位置维护，阶段和发布引用标准、记录结果。

按实际内容选择文件和目录的粒度：一份综合指南使用 guide.md，多份需要分别维护的指南出现后再分目录。文档角色不等于必须单建一个文件。起步保证项目入口、目标、SOP、阶段计划和任务清单可找，其他角色在出现实际内容时补齐。SOP 中的骨架和示例用于填写参考，尖括号和示例编号须按项目事实替换；占位文本不表示决定、任务或验证结果已经成立。没有发布就不预建发布记录，没有显著复盘内容就在计划中收尾。

## 标识、元数据与状态

### 稳定身份

阶段采用 `P001`，目录例如 `p001-docs-foundation`。任务采用项目范围内递增的 `T0001`，与阶段独立。故事和规则仅在确实需要引用时加稳定标识。标题可以调整，已经被引用的身份保持不变。

创建前检索现有编号，选择未占用的标识。并行新增时由同一协调者分配，写入前复核，避免撞号。移动任务保持原 ID，使用 Markdown 链接定位接收位置。此约定不提供并发锁。

### 最少字段

阶段 `plan.md` 使用 YAML 的 `id`、`status`，归档时增加 `archived: true`。不要求每份文档都有状态、负责人或更新时间。重要决定按需要记录 `accepted` / `superseded`，研究和验收记录使用实际日期与性质。

阶段状态只在 `plan.md`，任务状态只在所属 `tasks.md`。导航和路线图通过链接定位，不再抄录状态。

### 状态含义

阶段和任务共同使用 `todo / doing / done / cancelled`。

- `todo` 已纳入计划，尚未开展。
- `doing` 正在推进。遇到阻塞仍保持该状态，并记录阻塞原因、已知事实和接续条件。
- `done` 约定成果与必需验证已完成，有可定位的依据。
- `cancelled` 明确决定不再继续，记录原因、决定依据及已产出内容/遗留工作的去向。

通常经过 todo → doing → done，取消只在确有决定时使用。归档是独立属性，保留 done 或 cancelled 的真实结果。任务随所属阶段归档，不增加单独的任务归档字段。

任务在 Markdown 二级标题下用列表组织，状态只写一次，不用状态表与勾选框重复表达。具体格式由 [task SOP 的输出结构](sop/task.md#输出结构与示例)维护。

## AI 进入与写回

先区分本次请求是讨论、只读审查，还是执行与写回。讨论和只读审查只提供结果或草案，已有执行授权则继续完成对应工作，不因技能触发再造授权。

开始先读取项目 `AGENTS.md` 与适用 SOP。新项目或方向讨论再读 PRD、导航和路线图。已有任务直接定位阶段计划和任务，再按关联读取规格、设计、决定和证据，不要求每次通读全仓。

项目可在已有入口中注明采用的 SOP 来源、内容版本和项目差异。插件升级不会自动升级项目规则。已有明确规则优先据其解释资料，版本未知时先读取事实，不假定采用插件最新规则。若差异影响本次读写或验收含义，说明冲突并暂停受影响的写入，继续不受影响的工作。

恢复时明确本次目标、允许范围、完成条件、当前事实和下一步。任务已完成、取消或阶段已归档时，先辨别是在查历史、纠正错误还是开展新工作，不把旧状态直接恢复成进行中。

将事实、已确认决定、假设、建议和待决问题分开表达。代码与实际运行提供实现证据，规格提供行为契约，阶段差异提供未来目标。发现冲突调查其原因，不能以最后编辑时间任选一方，也不能把缺陷改写成新标准。

在这些检查点更新对应所有者，确认决定、开工、取得重要结果、发现阻塞、完成、交接和收工。写前读取最新文件，避免覆盖其他人的更新。每次写回只更新受影响的事实源和消费者。事实源唯一不意味着只有某个技能能修改它，当前执行者遵守同一完成条件和写回约定即可，不为修改状态循环调用技能。

AI 在已有授权内细化任务和执行检查。改变产品方向、关键架构、范围、退出条件或外部写入边界时，说明新增影响并按项目约定取得确认。当前指令已经明确授权的工作继续推进，不再增加一次形式审批。

## 当前基线与阶段差异

未来行为在所属阶段记录相对基线的增加、修改、删除，保留确认依据。交付时把实现、验证和当前规格/架构更新放进同一组可审查结果，对应差异注明并入位置，成为历史记录。

多个阶段修改相同规则时，明确各自写入责任，基线变化后重新核对未交付差异。Git 合并成功不证明语义一致。

## 完成与证据

完成结论须由原定条件和实际证据支持。先保存并读回结果，再写完成状态；未来才会生成的报告不算完成证据。失败、未验证、未知分别描述，复验保留旧失败，记录错误注明更正原因和依据。

静态检查、实际行为、外部运行与部署分别解释。审阅工作可以因形成了有依据的判断而完成，即使对象存在缺陷；被审阅对象仍按自己的条件判断。受检对象与标准版本、原文快照和验证记录的操作要求由 [verify](sop/verify.md)维护。

## 归档与历史

归档是独立属性，阶段收尾后在 plan 增加 `archived: true`，任务随所属阶段归档。保留目录、链接、标准修订依据和证据，roadmap 只调整入口，不复制状态。具体收尾顺序由 [review](sop/review.md)维护。

修改归档资料须区分导航/错字修正与历史事实更正，后者写明原因、日期和依据。新的工作用新任务承接，保留与原阶段的关联。证据与原文快照按当时版本解释，不因当前规范重组而重写。

## 阶段、版本与发布

单阶段发布意图写 plan，跨阶段发布意图写 roadmap，选一个所有者。说明希望交付哪些成果及必要验收要求即可，不按版本号复制整套阶段任务。

发布实际发生后追加 `docs/releases.md`，记录版本、日期、选入范围、产物或对象版本、适用验证证据、已知限制及必要使用说明。直接引用已有行为标准和阶段结果，具体产物有新集成风险时补查相应部分。

0.1.0、1.0.0 的产品范围由项目自己决定，共同约定不强加通用功能门槛。阶段完成、提交、打 tag、实际发布是不同事实，发布仍依具体授权执行。

## 规则改进与分发

规则修订由采用项目中的真实观察推动。先记录发生条件与实际影响，再判断应修改项目实例、具体 SOP（含输出结构）、指南还是共同约定，避免将单个项目偏好直接升级为通用要求。

需要修订时用 [plan](sop/plan.md)、[design](sop/design.md)、[task](sop/task.md)、[verify](sop/verify.md) 和 [review](sop/review.md) 处理，更新受影响消费者，再运行暴露该问题的原场景。验证记录明确局限，不把一次接续成功推成所有 Agent 长期可靠。

共同约定与 SOP（含输出结构）的作者源在 StoneDocs，技能源码在 StonePlugins。独立流程包括 idea、compare、decide、story、plan、design、task、verify、review；对应技能是否可用以实际安装环境为准。文档工作流与已有 engineering 工程约束共同使用。

技能包携带需要的固定共同约定与 SOP 副本，记录来源仓库、基线提交和文件哈希。若包含尚未提交的作者源修改，应明确标注工作树快照，不能声称来自基线提交。发布前固定到实际源版本。运行所需资源随包提供，不能依赖作者电脑路径或远端 latest。项目自身的目标、任务、决定和证据仍由项目拥有。

CLI、hook、Linear 是后续实验。当前任务状态在仓库，若将来调整所有权，明确来源切换、权限、冲突、失败与恢复约定。阶段可映射 Linear project 是待验证假设，不自动开启双向同步。

## 参考与证据边界

采用项目的研究和讨论记录保留各自来源、查阅日期与选择过程。历史候选布局与建议不覆盖当前规则，技能运行不要求读取作者项目的全部历史。

通用规则是否适用由真实实践检验，采用项目的实际结果从其阶段总览进入。链接、状态、格式检查只支持对应静态结论，AI 接续、任务写回和工具行为需要实际观察。
