# 个人项目文档与 AI 协作 SOP

本文件维护通用文档职责与工作流。项目目标、阶段进度和验证结果由采用项目自己的资料持有，验证范围以实际记录为准。作者源位于 StoneDocs，分发副本应注明来源与内容版本，不独立修改通用正文。

[最小模板](templates.md)提供内容骨架。具体项目的操作路线和术语分别由其指南与术语表维护。规则改动回到作者源，模板、指南和项目实例按影响更新。

## 1. 基本模型

- 产品目标解释为什么做。阶段按成果组织，可以并行，每阶段拥有一份任务清单。
- 任务以可验收结果拆分，与提交数量无关。一项任务可以服务多个用户故事，一个故事也可以由多个任务完成。
- release 与阶段多对多。一阶段可提供多个 beta 或正式版本，一次发布也可汇集多个阶段的成果。
- 当前规格拥有已交付基线的行为规则，阶段保留未来差异。实际结果由验收证据说明，契约存在不代表每次执行都成功。
- 每种事实只有一个可独立修改的所有者。允许引用、带来源摘要和标明时点的历史记录，不维护第二份活跃规则或任务状态。
- 初始使用 Markdown + Git。工作流可以从任一适用步骤进入，文档按真实内容创建。

## 2. 文档职责

采用浅层职责目录、英文小写路径、中文正文。根级约定文件保留 `README.md`、`AGENTS.md`、`CONTEXT.md`。

| 路径 | 内容所有权 | 创建与更新时机 |
| --- | --- | --- |
| `README.md` | 项目是什么、如何开始使用、必要入口 | 项目建立、可使用内容或使用入口变化 |
| `AGENTS.md` | 本项目约束、适用 SOP、AI 读取路线 | AI 协作开始、入口或项目约束变化 |
| `docs/README.md` | 读者阅读路线和文档位置 | 文档需要导航、文件职责或位置变化 |
| `docs/product.md` | PRD，目标用户、问题、目标、范围与非目标、成功标准、持久取舍 | 产品方向确认或改变 |
| `docs/roadmap.md` | 整体优先级、推进主线、阶段入口与依赖、跨阶段发布意图 | 规划阶段、优先级或关系改变 |
| `docs/specs/<capability>.md` | 当前业务能力的规则入口、正常/失败/边界场景、质量约束 | 能力交付时与实现同步更新 |
| `docs/architecture.md` | 当前系统边界、模块责任、数据所有权、交互和约束 | 当前架构随交付改变 |
| `docs/decisions/<id>-<topic>.md` | 重要产品或技术决定的背景、真实选项、选择、理由、代价、替代关系 | 存在长期需要解释的取舍 |
| `docs/phases/<id>-<outcome>/plan.md` | 背景、成果与故事、范围、退出条件、依赖、推进思路、风险、材料入口和收尾 | 阶段开始规划，范围或结论改变 |
| 同阶段 `design.md` / `designs/<topic>.md` | 需要一起审查的设计，结构、数据/契约、流程、失败、兼容/迁移、实现与验证方式 | 存在独立审查的技术方案，多任务可共用 |
| 同阶段 `tasks.md` | 本阶段任务的身份、状态、完成条件、依赖和证据 | 拆分、开工、阻塞、完成、交接时 |
| 同阶段 `spec-deltas.md` 或计划内差异节 | 相对哪个当前基线新增/修改/删除什么规则和场景、确认依据 | 新行为讨论确定，交付时转为历史引用 |
| 同阶段 `verification/<target>.md` | 某交付目标的各次验证，对象与标准版本、方法环境、实际结果、证据和限制 | 每次取得相关验证结果时追加 |
| 同阶段 `review.md` 或计划收尾节 | 成果结论、偏差、重要经验和遗留去向 | 阶段 review，内容有独立价值时拆文件 |
| `docs/research/<question>.md` / 阶段内 `research/` | 同一问题的调研与实验，问题、来源、假设、方法、观察、结论及局限 | 不确定性需要证据，结论不自动成为决定 |
| `docs/guides/<operation>.md` | 使用/开发操作，前置条件、步骤、预期结果、失败处理 | 有可执行操作需要说明时 |
| `CONTEXT.md` | 领域及项目特有技术概念、含义、别名、易混区别、详细资料入口 | 出现会影响理解的术语 |
| `docs/ideas.md` | 尚未安排的想法、价值、必要背景和待讨论问题 | 随手记录，采纳/放弃/实现后明确去向并移出待处理区 |
| `docs/releases.md` | 实际发生的版本、交付范围、产物、适用证据和已知限制 | 确有发布时追加 |

计划包含必要的技术概述，详细实现由 design 承担。`spec` 表达可观察行为，`design` 表达怎么实现。行为验收标准在一个位置维护，阶段和发布引用标准、记录结果。

文档角色不等于必须单建一个文件。起步保证项目入口、目标、SOP、阶段计划和任务清单可找，其他角色在出现实际内容时补齐。没有发布就不预建发布记录，没有显著复盘内容就在计划中收尾。

## 3. 标识、元数据与状态

### 稳定身份

阶段采用 `P001`，目录例如 `p001-docs-foundation`。任务采用项目范围内递增的 `T0001`，与阶段独立。故事和规则仅在确实需要引用时加稳定标识。标题可以调整，已经被引用的身份保持不变。

创建前检索现有编号，选择未占用的标识。并行新增时由同一协调者分配，写入前复核，避免撞号。移动任务保持原 ID，使用 Markdown 链接定位接收位置。此约定不提供并发锁。

### 最少字段

阶段 `plan.md` 使用 YAML 的 `id`、`status`，归档时增加 `archived: true`。不要求每份文档都有状态、负责人或更新时间。重要决定按需要记录 `accepted` / `superseded`，研究和验收记录使用实际日期与性质。

阶段状态只在 `plan.md`，任务状态只在所属 `tasks.md`。导航和路线图通过链接定位，不再抄录状态。

### 状态含义

阶段和任务共同使用 `todo / doing / done / cancelled`。

- `todo` 已纳入计划，尚未开展。
- `doing` 正在推进。遇到阻塞仍保持该状态，并记录阻塞原因、已知事实和接续条件。
- `done` 约定成果与必需验证已完成，有可定位的依据。
- `cancelled` 明确决定不再继续，记录原因、决定依据及已产出内容/遗留工作的去向。

通常经过 todo → doing → done，取消只在确有决定时使用。归档是独立属性，保留 done 或 cancelled 的真实结果。任务随所属阶段归档，不增加单独的任务归档字段。

任务在 Markdown 二级标题下用列表组织，状态只写一次，不用状态表与勾选框重复表达。具体格式见[模板](templates.md)。

## 4. AI 进入、读取与写回

先区分本次请求是讨论、只读审查，还是执行与写回。讨论和只读审查只提供结果或草案，已有执行授权则继续完成对应工作，不因技能触发再造授权。

开始先读取项目 `AGENTS.md` 与适用 SOP。新项目或方向讨论再读 PRD、导航和路线图。已有任务直接定位阶段计划和任务，再按关联读取规格、设计、决定和证据，不要求每次通读全仓。

项目可在已有入口中注明采用的 SOP 来源、内容版本和项目差异。插件升级不会自动升级项目规则。已有明确规则优先据其解释资料，版本未知时先读取事实，不假定采用插件最新规则。若差异影响本次读写或验收含义，说明冲突并暂停受影响的写入，继续不受影响的工作。

恢复时明确本次目标、允许范围、完成条件、当前事实和下一步。任务已完成、取消或阶段已归档时，先辨别是在查历史、纠正错误还是开展新工作，不把旧状态直接恢复成进行中。

将事实、已确认决定、假设、建议和待决问题分开表达。代码与实际运行提供实现证据，规格提供行为契约，阶段差异提供未来目标。发现冲突调查其原因，不能以最后编辑时间任选一方，也不能把缺陷改写成新标准。

在这些检查点更新对应所有者，确认决定、开工、取得重要结果、发现阻塞、完成、交接和收工。写前读取最新文件，避免覆盖其他人的更新。每次写回只更新受影响的事实源和消费者。事实源唯一不意味着只有某个技能能修改它，当前执行者遵守同一完成条件和写回约定即可，不为修改状态循环调用技能。

AI 在已有授权内细化任务和执行检查。改变产品方向、关键架构、范围、退出条件或外部写入边界时，说明新增影响并按项目约定取得确认。当前指令已经明确授权的工作继续推进，不再增加一次形式审批。

## 5. 九项工作流能力

这些名称表示协作职责和自然语言入口；是否已有对应技能或命令，以采用项目的实际安装环境为准。无需按九步顺序执行，小改动可以直接从 task 进入。

| 能力 | 什么时候触发 | 读什么 | 写到哪里、留下什么 |
| --- | --- | --- | --- |
| `idea` | “我有个想法，先记下来” | 相关目标、现有想法，检查是否重复 | `ideas.md` 待处理项。已有明确任务则关联，不再复制待办 |
| `compare` | “有哪些方案，有什么依据” | 问题约束、当前规格/架构、已有研究和一手资料 | 对应问题的 research，区分资料事实、实验观察、推断和建议 |
| `decide` | “继续追问，帮我做取舍” | 已确认目标、比较结果、受影响资料 | 决定更新到该内容的所有者。有长期解释价值再建 decisions，未决项留在所属计划/研究 |
| `story` | 需要把成果变成可理解、可验证的用户行为 | PRD、术语、当前规格和已确认范围 | 故事在 plan，未来规则/场景在阶段差异，已交付规则/场景在 specs |
| `plan` | 规划一个成果阶段或调整推进主线 | PRD、roadmap、现有阶段与依赖、适用规格 | 阶段 plan，roadmap 只更新优先级和关系入口 |
| `design` | 需要一起审查实现方案 | plan、规则/差异、当前架构和约束 | 阶段 design，持久取舍引用 decision。未来设计不会直接覆盖当前架构 |
| `task` | 拆任务、继续执行、记录阻塞或交接 | plan、design、标准、当前任务和证据 | 阶段 tasks 及实际交付文件，状态和接续信息在 tasks，验证批次在 verification |
| `verify` | 已有可检验的交付或需要复核修正 | 任务完成条件、适用标准及版本、受检对象 | verification 追加方法、结果、证据和限制。未满足条件的实现任务不能写 done |
| `review` | 回看阶段成果、判断收尾或取消 | plan 退出条件、任务处置、验收、当前规格和架构 | plan 收尾结论，按需 review，处理遗留并原地归档，roadmap 调整阅读入口 |

能力之间通过这些文件交接，不要求下一会话记住聊天。执行代码、调用 CLI 或操作 Linear 使用项目已有能力和授权，SOP 不虚构可调用工具。

### 故事与验收示例

用角色、希望取得的结果和价值组织用户故事。技术、研究或文档工作可直接写交付目标，不强套用户角色。故事是阶段规划材料，不再维护一份长期故事状态表。

围绕故事识别业务规则、代表性示例和未决问题。Markdown 可用“前提／动作／期望”，每个示例保留必要前提、一个主要动作、具体可观察结果，同时考虑失败与边界。规则服务故事，但同一规则只维护一次。

采用这种写法不依赖 Cucumber。示例文字清楚不等于验证执行成功，实际结果仍需记录。

## 6. 执行、差异与完成

已有任务开工前核对完成条件与依赖，按可验收结果拆分。执行中的进度、阻塞和下一步写在任务详情，聊天只作摘要。

未来行为在所属阶段记录相对基线的增加、修改、删除，保留确认依据。交付时把实现、验证和当前规格/架构更新放进同一组可审查结果，不等整个阶段结束。对应差异注明并入位置，成为历史记录。

多个阶段修改相同规则时，明确各自写入责任，基线变化后重新核对未交付差异。Git 合并成功不证明语义一致。

验证以交付目标为入口，一份记录可以追加多批结果。每批明确受检对象与版本、标准与版本、方法/环境、观察、证据及未覆盖范围。优先引用可取回的提交、构建或文档版本。没有可取回且覆盖本次内容的版本时，保存受检文件的只读快照及哈希清单，哈希用于校验，不能代替原文。HEAD 不能代表未提交修改或未跟踪文件。只固定本次受检范围，避免复制无关资料或凭据。历史快照按批次保存，不参与当前规则维护。成功批次不覆盖失败记录，证据错误则追加更正说明。

完成任务前先写入并读回实际结果与证据，再检查原定条件、必需验证与权威文档同步。未来才会生成的证据不能支持完成结论。未验证、失败、未知分别记录。审阅任务可以因完成审阅而 done，即使发现缺陷，缺陷由实际修复任务承接，不能据此宣布被审阅对象验收通过。

## 7. 移交、阶段 review 与归档

### 任务移交

不同阶段可以引用彼此产物，不重复创建同一工作的活跃任务。确需转移同一任务时，接收阶段保留原 ID、完成条件、已有证据和未完成事实。来源只留历史指针、原因和接收依据，删除其活跃状态字段，接收方成为唯一状态源。

转移后，来源阶段归档不影响接收任务继续推进。已完成任务后来出现新的工作，建立关联任务。原验收有误则明确更正，保留当时结果及更正依据。

### 阶段 review

核对成果和原定退出条件、实际证据、当前规格/架构同步、剩余事项的去向。verify 提供交付证据，review 据此判断阶段结论，复用适用证据，补充真正缺失的验证。

非阻断事项可在明确移交后结束阶段。影响原退出条件的任务必须完成，或先明确讨论调整范围与退出条件，保留依据。不能靠把任务移走、换称“优化”来宣布成果达成。

需要单独建立阶段审阅任务时，其成果定义为有证据的阶段判断和遗留处置，判断暂不能收尾也可以满足该审阅任务的条件。无需每阶段强制建立审阅任务。实际归档作为满足阶段条件后的动作，避免把任务完成与归档互设前置。既有约定出现这种循环时须明确处理，不能临时标记成功来绕过。

先写入并读回阶段判断，若有对应审阅任务则按它的实际完成条件写回。满足条件且已获收尾授权后把阶段设为 done，取消则设为 cancelled 并记录原因。收尾短则写 plan，有显著偏差、重复问题或可复用经验再写 review。重构和优化由实际问题驱动。

### 原地归档

收尾后在 plan 增加 `archived: true`，保留目录、链接、标准修订依据和验收记录。roadmap 将入口放入历史成果区，不复制状态。任务随阶段归档，归档不删除内容，也不自动发布。归档后核对实际状态和入口，发现偏差直接记录并修正，不为后置核对再次启动整轮 review，也不沿用不成立的完成结论。

修改归档资料须区分导航/错字修正与历史事实更正，后者写明原因和日期。新的工作用新任务承接，保留与原阶段的关联。

## 8. 轻量版本规划与发布

单阶段发布意图写 plan，跨阶段发布意图写 roadmap，选一个所有者。说明希望交付哪些成果及必要验收要求即可，不按版本号复制整套阶段任务。

发布实际发生后追加 `docs/releases.md`，记录版本、日期、选入范围、产物及适用验证证据、已知限制。直接引用已有行为标准和阶段结果，具体产物有新集成风险时补查相应部分。

0.1.0、1.0.0 的产品范围由项目自己决定，本 SOP 不强加通用功能门槛。阶段完成、提交、打 tag、实际发布是不同事实，发布仍依具体授权执行。

## 9. 用工作流改善工作流

规则修订由采用项目中的真实观察推动。先记录发生条件与实际影响，再判断应修改项目实例、模板、指南还是通用规则，避免将单个项目偏好直接升级为通用要求。

需要修订时用现有 task/plan/design/verify/review 流程处理，更新受影响消费者，再运行暴露该问题的原场景。验证记录明确局限，不把一次接续成功推成所有 Agent 长期可靠。

通用 SOP 与模板的作者源在 StoneDocs，技能源码在 StonePlugins。首批入口为 task、verify、review，其余名称保留为 idea、compare、decide、story、plan、design。文档工作流与已有 engineering 工程约束共同使用。

技能包携带需要的固定 SOP/模板副本，记录来源仓库、基线提交和文件哈希。若包含尚未提交的作者源修改，应明确标注工作树快照，不能声称来自基线提交。发布前固定到实际源版本。运行所需资源随包提供，不能依赖作者电脑路径或远端 latest。项目自身的目标、任务、决定和证据仍由项目拥有。

CLI、hook、Linear 是后续实验。当前任务状态在仓库，若将来调整所有权，明确来源切换、权限、冲突、失败与恢复约定。阶段可映射 Linear project 是待验证假设，不自动开启双向同步。

## 10. 参考与证据边界

采用项目的研究和讨论记录保留各自来源、查阅日期与选择过程。历史候选布局与建议不覆盖当前规则，技能运行不要求读取作者项目的全部历史。

通用规则是否适用由真实实践检验，采用项目的实际结果从其阶段总览进入。链接、状态、格式检查只支持对应静态结论，AI 接续、任务写回和工具行为需要实际观察。
