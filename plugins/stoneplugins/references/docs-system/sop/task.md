# 拆分、执行与交接任务

## 适用与依据

拆分或继续已明确的工作，记录阻塞，或交接未完成任务。 共同权限、状态与版本规则见[共同约定](../conventions.md)。

## 读取

项目入口、阶段 plan/tasks、相关 design、行为标准、决定与已有证据。

## 操作

1. 按任务 ID 或成果定位唯一记录，明确本次授权、完成条件、依赖和实际状态；已移交沿指针定位接收方，历史任务按共同约定处理。
2. 按可验收成果拆分任务，使用稳定 ID。任务归所属阶段，提交和发布数量不决定任务边界。
3. 开工写回实际状态，执行中在任务记录中维护重要结果、阻塞原因和接续条件。实现继续遵守项目工程约束。
4. 交付时把实现、必要验证和受影响的当前规格、架构或指南组成同组可审查结果；阶段未来差异同步为交付引用。
5. 按 [verify](verify.md) 获取适用证据，可在同一会话连续执行；有效证据无相关变化时复用。先保存并读回结果，再按共同完成条件写 done。
6. 移交同一未完成任务时，接收方保留原 ID、完成条件、既有证据和未完成事实；来源只留历史指针、原因和接收依据，去掉活跃状态字段。来源归档不改变接收任务状态。

## 产出与完成

任务状态与接续点留在唯一 tasks 中，实际验证进入 verification。完成任务不自动收尾阶段；新增范围或关键方案变化按共同约定处理。

## 输出结构与示例

本节提供 tasks.md 中单条任务的格式；后续任务沿用同一格式并使用项目实际编号。

```markdown
# <阶段标识> 任务清单

阶段目标与退出条件见[计划](plan.md)。

## T0001 · <可交付的成果>

- 状态：todo
- 交付物：<具体文件、功能或可审查结果>。
- 完成条件：<能判断完成的条件；复用标准链接到具体规则或场景>。
- 材料：<计划、设计、相关规格和已有实现的链接>。
- 依赖：<需要先获得的任务成果或外部条件；没有则省略>。
- 验证证据：<对应验收批次、实际结果或可核对产物；未执行时明确写未验证>。
- 接续说明：<必要的当前事实、阻塞原因与下一步；没有则省略>。
```
