# 拆分、执行与交接任务

## 适用与读取

拆分、继续或交接已明确的阶段工作。读取所属 Goal/Phase plan、唯一 tasks.md、相关设计、标准、决定和结果；共用规则见[共同约定](../conventions.md)。

## 操作

1. 先核对项目根及适用规范，再按成果或 Task ID 定位本项目所属 Phase 与唯一条目，明确本次授权、完成条件、依赖和状态。实验任务与被试产品任务分别在各自项目接续，不能只凭相同编号选取条目。找不到承接阶段时先澄清或规划，不建立阶段外 Task。
2. 按可独立验收的成果拆分，每项须支撑本阶段已确认目标。共同服务一个结果的实施操作留作步骤；清单过长可加主题索引，不另设任务组状态。提交、文件和发布数量不决定边界。
3. 实施前核对当期范围、当前成果所需的关键选择、授权边界和验收方法。已有事实足够即可接续；缺口先调查，只暂停受影响的实现，并按需回到 [story](story.md)、[plan](plan.md) 或 [design](design.md)。普通可逆细节依项目约定合理判断，不让无关的未来阶段选择阻断当前工作，也不把候选方案当成确认。
4. 开工写实际状态，执行中维护重要事实、阻塞与下一步。小修并入合适的当前阶段；改变目标、关键方案或退出条件时先处理范围，不能不断加任务扩大承诺。本轮操作经过和授权依据按需留在任务接续或回复中，不写成阶段成果或退出条件。
5. 按完成条件实施并依 [verify](verify.md)取得必要结果。普通结果可直接在条目简记；有独立验收或多批次需要时链接对应记录，不重复抄写。
6. 交付时同步真正受影响的当前标准、架构或指南；仅结构/契约改变才更新架构，阶段差异注明并入位置。确认结果已写入后再按条件写 done，完成 Task 不自动完成 Phase。
7. 移交同一未完成 Task 时，接收 Phase 保留 ID、条件、既有结果及未完成事实；来源只留移交原因和接收链接，去掉第二份活跃条目和状态。归档阶段的新工作由后续承接，不直接重开旧任务。

## 输出结构与示例

每个 Phase 只维护一份 tasks.md，任务正文用二级标题和列表，不另用状态表或勾选框复制进度：

```markdown
# <Phase 标识> 任务清单

阶段成果与条件见[计划](plan.md)。

## T0001 · <可交付成果>

- 状态：todo
- 交付物：<文件、能力或可审查结果>。
- 完成条件：<如何判断完成；链接适用标准或阶段条件>。
- 材料：<已有设计、规则、实现及必要背景>。
- 依赖：<具体成果或外部条件；没有则省略>。
- 验证结果：<未验证；取得结果后简记日期、对象版本、方法、实际结果和限制，或链接验收批次>。
- 接续说明：<重要事实、阻塞与下一步；没有则省略>。
```

Goal 整体验收也由某个 Phase 的 Task 承接，报告链接 Goal verification；Task 完成与 Goal 通过按各自条件判断。

## 完成判断

任务结果和状态真实，证据位置可找到，接续或接收关系明确；普通步骤不成为另一套有状态子任务。无法完成时保留未完成事实，不用归档或移走任务规避条件。
