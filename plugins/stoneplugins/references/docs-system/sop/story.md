# 梳理用户故事与行为场景

## 适用与依据

需要把目标转成使用者能够理解、可以检验的行为。 共同权限、状态与版本规则见[共同约定](../conventions.md)。

## 读取

PRD、术语、当前能力规格、已确认范围与问题。

## 操作

1. 用“作为谁，希望得到什么结果，以便获得什么价值”描述故事。技术、研究和文档工作可以直接写交付目标，不强套角色。
2. 识别故事对应的业务规则、代表性例子和未决问题，考虑正常、失败和边界情况。
3. 围绕必要前提、一个主要动作和可观察结果组织场景，具体写法见本页输出结构，不拆成实现步骤。
4. 故事进入阶段计划；复用规则引用当前规格，未来行为差异留在阶段，交付时按 [task](task.md) 同步当前基线。

## 产出与完成

完成意味着价值、边界和可判断结果明确。验收标准只有一个所有者，不额外维护故事状态表；这些写法不依赖 Cucumber。

## 输出结构与示例

故事和场景写入计划或其适用的规则所有者，不创建第二份故事状态表。

```markdown
### <故事名称>

作为<角色>，我希望<能力或行为>，以便<获得的价值>。

<必要时说明使用情境、优先理由和边界；技术、研究或文档工作可直接填写交付目标。>
```

同一规则可以有多个代表性场景：

```markdown
### <一条业务规则>

<使用者可以理解的行为约定。>

#### 场景：<例子名称>

- Given：<必要前提>。
- When：<一个主要动作或事件>。
- Then：<可观察、可判断的结果>。
```
