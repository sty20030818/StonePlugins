# 文档最小模板

这里维护各类文档的最小结构和可复制骨架。职责、状态含义、工作流程与权限边界以 [SOP](sop.md) 为准；实际操作由采用项目的指南说明。

## 使用方式

- 从已有文档和本次成果出发选模板，有实际内容才创建文件；不一次铺开空目录与空文档。
- 替换尖括号中的占位内容和示例编号。示例不代表批准决定、已存在的任务或实际验证结果；没有证据的内容保持待确认或未验证。
- 新路径使用英文小写及连字符，正文默认中文；`README.md`、`AGENTS.md`、`CONTEXT.md` 沿用固定入口名。阶段路径示例为 `docs/phases/p001-docs-foundation/`，阶段标识为 `P001`；任务使用独立编号，如 `T0001`，不包含阶段编号。
- 阶段与任务状态字段只填 `todo`、`doing`、`done`、`cancelled`。阶段状态只在 plan 的 frontmatter，任务状态只在所属 tasks 的单条记录；归档时在阶段 frontmatter 另加 `archived: true`。状态转换与归档条件见 SOP。
- 能复用的规则和场景只在当前规格定义一次。阶段独有的退出条件或未来目标差异写在 plan，其他文档引用。模板中的可选节按实际需要保留，不以“待补充”替代必要决定。

## 阶段计划 `plan.md`

先填写成果、故事、范围和退出条件，再补足影响推进的依赖与差异。用户故事表达谁需要什么、为什么需要；技术、研究或文档工作可直接填写交付目标。设计与任务分别引用本计划。

```markdown
---
id: P001
status: todo
---

# <本阶段要达成的成果>

## 背景与依据

<要解决的问题、关联的产品目标、已有事实与本阶段授权或确认依据。>

## 成果与用户故事

<阶段完成后，用户或项目会获得什么可观察的成果。>

### <故事名称>

作为<角色>，我希望<能力或行为>，以便<获得的价值>。

<必要时说明使用情境、优先理由和边界；验收规则引用下方唯一来源。>

## 范围

- 包含：<本阶段承诺覆盖的能力与边界>。
- 不包含：<容易被误认为属于本阶段的内容>。

## 验收与退出条件

1. <可观察、可判断的阶段成果或退出条件>。
2. <引用当前规格中的具体规则或场景，以及本阶段适用范围>。

<仅本阶段适用的标准在这里定义；复用标准引用其来源，不再抄写。>

## 推进与依赖

<成果之间的先后关系、依赖的具体产物、外部条件和主要风险。
任务及其当前状态见 tasks.md。>

## 目标差异

<没有行为变化时说明原因；有变化时按能力列出：>

- 当前基线：<能力规格及准确规则位置>。
- 拟新增、修改或移除：<相对基线的差异，未变化部分只引用>。
- 确认依据：<已确认的决定，或仍需讨论的问题>。
- 规则与场景：<该差异应满足的可观察行为及边界>。
- 并入记录：<交付后补充进入当前规格的位置和对象版本>。

## 未决问题

<会改变范围、设计或验收的问题及解决所需信息；无则删去本节。>

## 发布意图

<仅在有发布意图时保留：候选版本、拟选成果、放行条件及确认依据。
关联其他阶段时引用具体成果；发布发生后链接 docs/releases.md 中的记录。>

## 阶段材料

- [实施设计](design.md)（需要独立设计时保留）
- [任务清单](tasks.md)
- <已经存在的验收记录、阶段 review 等入口>

## 收尾

<审查后补充成果与退出条件的判断、证据、基线同步及遗留去向。
需要独立 review 时，正文只在 review.md 维护，这里链接到它。>
```

目标差异中的场景可用以下写法；Given / When / Then 描述行为，不拆成实现步骤。相同规则需要多个例子时，在该规则下补充正常、异常和边界场景。

```markdown
### <一条业务规则>

<使用者可以理解的行为约定。>

#### 场景：<例子名称>

- Given：<必要前提>。
- When：<一个主要动作或事件>。
- Then：<可观察、可判断的结果>。
```

## 阶段设计 `design.md`

记录本阶段怎么实现及选择理由。设计引用故事、规则和验收要求；涉及长期架构或重要决定时，指向其所有者。接口、数据、迁移等小节只按本次真实影响展开。

```markdown
# <阶段标识> 实施设计

## 目标与约束

<引用 plan.md 的目标和范围，列出设计必须遵守的已有约束。>

## 实施方案

<模块或文档如何分工，输入输出与主要执行路径，哪些现有内容需要调整。
按实际需要说明接口、数据、权限、兼容性或协作边界。>

## 选择与理由

<采用的方案、影响选择的替代项、取舍及确认依据。
已有重要决定引用 decisions 中的记录，不维护第二份决定正文。>

## 影响与恢复

<受影响的使用者、文件或数据；有迁移或覆盖时说明精确范围、恢复办法与限制。
没有相关影响时可说明原因并保持简短。>

## 验证安排

<引用标准来源，说明用什么方法验证关键风险、需要什么环境或前置条件。
实际执行结果进入 verification，不提前填写成功。>

## 待决事项

<尚未解决且影响实施的决定或风险；无则删去本节。>
```

## 阶段任务 `tasks.md`

同一文件按任务分节。标题给出具体成果，任务记录包含唯一状态、完成条件、材料和证据；依赖、阻塞原因与接续点按需加在该任务下。

```markdown
# <阶段标识> 任务清单

阶段目标与退出条件见[计划](plan.md)。

## T0001 · <可交付的成果>

- 状态：todo
- 交付物：<具体文件、功能或可审查结果>。
- 完成条件：<能判断完成的条件；复用标准链接到具体规则或场景>。
- 材料：<计划、设计、相关规格和已有实现的链接>。
- 依赖：<需要先获得的任务成果或外部条件；没有则省略>。
- 验证证据：<对应验收批次、实际结果或可核对产物；未执行时明确写未验证>。
- 接续说明：<必要的当前事实、阻塞原因与下一步；没有则省略>。

## T0002 · <下一项可交付的成果>

- 状态：todo
- 交付物：<具体产物>。
- 完成条件：<可判断的完成条件>。
- 材料：<所需材料链接>。
- 验证证据：未验证。
```

取消时在本任务补充取消依据与已产生内容的处置。移交同一项未完成工作时，保留任务标识，把完整记录放到接收阶段；原位置只留下“已移交至……”的链接，不保留第二个状态字段。任务增补或移交后继续按 SOP 检查阶段范围与验收要求。

## 实际验收 `verification/<topic>.md`

验收文件保存运行事实。标准正文留在规格或计划中，这里记录每批使用的标准版本及观察结果。追加复验批次，保留此前失败；历史结果不能随当前文件变化被重新解释为对新版本的证明。

```markdown
# <交付目标>验收记录

## 交付目标与范围

<这组验收要回答什么，关联哪个阶段成果或任务。
链接标准来源，并说明此次覆盖与排除的范围。>

## 批次 <日期与本文件内唯一序号>

### 对象与标准版本

- 对象：<受检代码、文档、产物或服务>。
- 对象版本：<可核对的提交、构建、快照，或未提交文件的可恢复快照、清单与哈希>。
- 标准来源与版本：<规格或阶段条件的位置，以及本批使用的具体版本标识>。

### 方法与环境

- 方法：<实际采用的检查、操作步骤或测试方法>。
- 环境：<对结论有影响的平台、配置、工具版本和前置条件>。
- 执行信息：<实际日期、执行者或执行方式>。

### 结果与证据

#### <被核对的条件或场景链接>

- 实际观察：<发生了什么，实际输出或行为是什么>。
- 结果：<通过、失败或未验证；不适用须说明依据>。
- 证据：<日志、产物、截图、检查输出或可复核的记录位置>。

### 限制与后续

<未覆盖或无法确认的内容，以及结论适用范围。
发现需要处理的问题时链接所属任务；复验在后续批次记录。>
```

没有可取回的提交或构建版本时，按 SOP 保存受检原文快照与哈希。快照属于当时的只读证据，不是另一份活跃规范。

标准在两次验收之间变化时，新批次标明新标准及变化依据。一次批次只能证明其列出的对象、标准和范围；本地检查、实际接续、外部部署等结果分别如实描述。

## 阶段复盘 `review.md`

review 保存本次收尾判断与改进依据；阶段当前状态仍在 plan，任务当前状态仍在 tasks。以下骨架既可记录未通过的阶段审查，也可记录完成或取消时的结论。若专门建立审阅任务，以形成有证据的判断和遗留处置为成果，避免把任务完成与阶段归档互设前置。

```markdown
# <阶段标识> 阶段复盘

## 审查范围

- 审查日期：<实际日期>。
- 对象与依据：<阶段计划版本、交付物版本及验收记录链接>。

## 成果与退出条件

### <plan 中的某项退出条件链接>

- 判断：<成立、不成立或仍无法确认>。
- 依据：<验收批次、实际产物与必要解释>。

<逐项核对原定条件；发生过范围或标准调整时引用决定与理由。>

## 偏差与质量发现

<实际成果与计划的差异、失败与修复、仍存在的限制，以及值得保留的方法。
根据实际问题判断是否需要重构或优化。>

## 遗留与交接

<每项遗留的影响、是否阻断退出、任务标识和明确接收位置。
这里只保存本次处置快照，后续状态沿链接查看。没有遗留时如实说明。>

## 当前基线同步

<已进入长期规格、架构或指南的内容及位置；确认阶段差异已转为历史引用。
尚未交付内容的去向及原因。>

## 收尾结论与下一步

<本次是否具备完成、取消或归档条件，判断依据及仍需处理的事项。
后续建议和已批准工作分开记录；阶段状态按 SOP 写回 plan。>
```

## 其他文档的最小结构

下表只规定填写骨架。每类文档的职责与权威关系见 SOP；没有相应内容时无需创建。

| 角色与路径 | 最少内容 |
| --- | --- |
| 项目入口 `README.md` | 项目是什么；现在如何使用；最短开始步骤；必要资料入口。 |
| AI 入口 `AGENTS.md` | 本项目执行约束；开始与恢复时的读取路线；任务和事实的写回入口。 |
| 文档导航 `docs/README.md` | 按阅读目的组织的入口；当前资料与历史材料的区别；阶段索引链接。 |
| 产品 PRD `docs/product.md` | 目标用户与问题；产品目标与价值；范围和非目标；可判断的成功标准。 |
| 能力规格 `docs/specs/<capability>.md` | 能力边界；当前基线规则；正常、异常与边界场景；相关约束和来源链接。 |
| 当前架构 `docs/architecture.md` | 系统边界；主要模块与职责；关键交互和约束；重要决定入口。 |
| 重要决定 `docs/decisions/<id>-<topic>.md` | 决定标识、日期与生效情况；背景和约束；选择及依据；后果；取代关系（适用时）。 |
| 阶段路线图 `docs/roadmap.md` | 产品目标关联；整体优先级与推进主线；阶段标识、成果与 plan 链接；跨阶段依赖；需要跨阶段表达的发布意图。 |
| 研究 `docs/research/<question>.md`，也可放在阶段内 | 研究问题；查阅日期与来源；假设、方法、观察和结论；限制；建议与待决问题。 |
| 操作指南 `docs/guides/<topic>.md` | 要完成的事情；适用前提；实际操作步骤与示例；可观察的结果；失败或接续办法；规则来源。 |
| 术语表 `CONTEXT.md` | 需要统一的名称；本项目定义；容易混淆的概念；必要来源链接。 |
| 想法池 `docs/ideas.md` | 想解决的问题与价值；事实、假设和待决问题；相关讨论或研究；进入决定或阶段后的去向。 |
| 发布记录 `docs/releases.md` | 实际版本与发布日期；选入的成果及阶段来源；产物或对象版本；验收证据；已知限制及必要使用说明。 |

发布意图选择一个直接所有者：局部意图写阶段 plan，跨阶段统筹写 roadmap，另一处引用。`docs/releases.md` 在实际发布后记录发生的事实，无发布时不预建空记录。
