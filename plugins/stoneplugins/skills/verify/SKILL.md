# Verify

读取项目入口及[共用 SOP](../../references/docs-system/sop.md)第 4、6 节，按需使用[验收模板](../../references/docs-system/templates.md)。资源来源见[固定快照清单](../../references/docs-system/source.json)。先区分只读核对与获准执行/写回，项目采用的规则版本不随插件升级自动改变。

## 读取与写入

读取任务完成条件、适用行为标准或阶段差异、受检对象及既有验证记录。标准属于其原有文档，不在验收记录中维护第二份可独立变化的规则。

获准写回时，在所属 verification 文件追加批次和必要证据。若只要求审查现有证据，返回判断与缺口，不自动运行有副作用的操作或修改项目。

## 取得可核对的证据

1. 明确本次要回答的问题、适用标准及必须覆盖的条件。标准不明确时说明缺口，不自行补造、降低或改写标准来取得通过。
2. 固定实际受检对象和标准版本。已有提交仅能代表提交内的内容，不能覆盖未提交修改或未跟踪文件。没有可完整取回的版本时，按 SOP 保存本次受检范围的原文快照与哈希，并独立读回校验，不固定某种归档工具或格式。
3. 选择与风险相称且在授权内的检查。能复用的现有检查直接使用，必要检查通过后不无故重复扩大。区分静态检查、实际行为、外部运行及待人工确认。
4. 如实记录方法、环境、逐条件观察、结果、证据及未覆盖范围。明确区分未执行、失败和未知。命令退出码、对象版本和实际输出须与结论相符。
5. 复验追加批次并保留旧失败。记录本身错误时注明更正原因和依据。发现修复需求交回相应任务，不在验证过程中悄悄扩展实现范围。
6. 读回结果和证据，检查文件/链接可定位、内容非占位、对象与标准匹配。未来才会生成的报告不能支撑完成结论。

## 结果

返回逐条件结论、证据入口、未满足项和局限。验证工作结束不等于被验收的实现任务或阶段完成。

如果本次验证自身有独立任务，当前执行者按该任务的原定完成条件写回。不能将“已执行验证”混同于一个要求“验证通过”的任务已经完成，也无需为状态写回重新启动 task 流程。
