# Review

读取项目入口及[共用 SOP](../../references/docs-system/sop.md)第 4、6、7 节，按需使用[复盘模板](../../references/docs-system/templates.md)。资源来源见[固定快照清单](../../references/docs-system/source.json)。按项目采用的规则版本及例外理解资料。本技能处理阶段审阅，普通代码或 PR 审查由相应工程审阅流程承接。

## 读取与写入

读取阶段 plan、tasks、适用验证记录、当前规格和架构，以及遗留工作的接收依据。状态与证据从其唯一所有者读取，不能从聊天摘要推断完成。

只读评审时返回结论。获准写回时，在 plan 收尾节或独立 review 中保存正文，按实际授权维护对应任务、阶段状态和 roadmap 入口，不再复制另一份活跃状态表。

## 形成阶段判断

1. 明确本次是只读评审、记录复盘，还是实际收尾归档。“能否收尾”的审查请求本身不自动授权归档。
2. 对照原定成果与退出条件核对实际交付，检查标准版本、对象和证据是否匹配。任务数量、提交或发布都不能替代成果判断。
3. 复用有效证据，仅对真正缺失或失效的部分补充 [verify](../verify/SKILL.md)。记录证据缺口，不通过修改退出条件制造成立。
4. 核对当前规格/架构同步和剩余事项。非阻断工作按明确去向交接，保留身份和未完成事实。影响原退出条件的工作不能靠移走规避。
5. 先写入有依据的阶段判断、遗留处置和必要经验，并读回确认。结论可以是满足条件，也可以是暂不能收尾，不能引用尚未生成的证据。
6. 若本次审阅自身有任务，按它的完成条件记录结果。“形成判断”可以完成审阅任务，但不会自动完成阶段。遇到任务完成与归档互设前置的既有约定，明确指出并处理契约冲突，不能临时填 done 绕过。
7. 已获收尾授权且条件满足后，再写阶段完成与归档信息，保留原目录和证据，调整 roadmap 入口。取消依明确决定记录原因和遗留去向，不能伪装为成果达成。
8. 回读实际状态和入口。后置核对发现偏差时记录并修正，不为此再次启动整轮 review，也不沿用不成立的完成结论。

## 结果

说明阶段结论、依据、遗留去向、实际归档结果及后续建议。已批准工作与待讨论建议分开表达，归档不自动提交、发布或操作外部系统。
