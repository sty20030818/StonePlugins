# 验证、诊断与审查

涉及 Bug、非平凡行为、测试、审查、迁移，或安全、权限、金钱、持久化和外部副作用时读取；按本次风险具体化核心的完整工程契约。

先把目标写成可观察结果：哪些输入、状态或操作应产生什么行为，哪些行为必须保持。选取风险相称的最小证据，说明代表性边界与未覆盖范围。

## 找到可验证的根因

- 先建立最小稳定复现或能在错误存在时失败的检查；沿真实调用路径找到共同所有者与同类消费者，提出可证伪假设，一次改变一个有诊断意义的变量。
- 连续检查没有新增证据时，停止细微变体和补丁叠加，说明失败依据与剩余假设，换能区分解释的检查；无法查明的关键缺口再请求信息。
- 修复留下能在旧行为下失败、新行为下通过的最小回归证据。根因仍不确定时直说；用户仅要求诊断时不实施修复。
- 测公共行为而非私有实现形状，复用已有框架和测试接缝，不为测试引入无业务价值的抽象。

## TDD 与垂直切片

目标明确、测试能快速稳定运行的非平凡行为，默认采用 Red → Green → Refactor：

1. 先写最小行为测试，运行并确认它因目标行为缺失或错误而失败。
2. 实现使其通过的最小完整切片；跨层功能贯穿真实输入、业务决定和结果，不用各层占位实现冒充端到端完成。
3. 在测试保护下整理当前因果边界，保持已确认行为；按下一个真实行为继续，补齐必要契约、集成与风险边界证据。

纯文案、编译器已完整覆盖的一行事实、探索可行性的原型或无法稳定观察的外部交互，不强制先写单元测试；选择对应的契约、集成或人工证据，免用 TDD 不等于免验证。

## Characterization Testing

重构、迁移或替换前，遗留行为不明且缺少可信规范或测试时，先在本次受影响的公共边界或最小安全接缝建立行为基线，不扩成全系统快照工程。

- 分清已确认保留、已确认改变和仍未知的行为；记录现状不代表认可现状。已确认 Bug 用目标行为的失败测试描述，不冻结成永久契约。
- 控制时钟、随机性、外部服务和共享状态，使检查可重复；只保留必要的输入与输出，避免巨大快照、私有调用顺序和偶然对象形状。
- 已有可信行为测试时直接复用；实现变化后保留有效行为覆盖，替换只验证旧内部结构的断言，不叠加重复测试套件。

## 不能弱化的契约

- 输入变化覆盖缺失、合法和非法值；`null`、空值、范围和类型按实际契约断言，不用宽松类型掩盖语义差异。
- 权限覆盖允许、拒绝和资源归属；拒绝路径不得泄露数据或产生副作用。契约要求 403 时精确断言 403，不能放宽成“小于 500”。若用户已授权变更契约，同步调用方、文档与新的精确断言。
- 副作用覆盖成功、已知失败及结果未知时的恢复；按风险检查重复、部分完成、取消与回滚，不靠固定等待或无限重试制造通过。
- 多个实现、provider、adapter 或 test double 承担同一角色时，通过公共边界运行同一组契约测试（Contract Testing）验证共同保证；差异能力与各自集成风险另补检查，测试替身不能省略生产必需的失败或副作用。
- 既有测试与已确认需求冲突时说明原因，再更新测试并保持对应覆盖；不得删除有效断言、隐藏失败或静默兜底。
- 间歇性失败调查时序、共享状态、随机性、时间和外部依赖；等待、轮询或有限重试须属于被测协议，或是有负责人和退出条件的临时隔离，不能掩盖根因。检查测试确实会在目标行为损坏时失败。

## 错误与失败语义

- 不空捕获或把未知失败变成成功、默认值；由当前所有者恢复、在边界转译为明确契约，或保留失败信号向上传播。只有确实可忽略且理由清楚的失败才有意忽略。
- 区分可恢复的预期错误与违反不变量的非预期错误：前者给调用方稳定、可操作的错误，后者保留受控诊断证据；不把异常伪装成正常状态。
- 日志由能补充责任边界、关联信息和恢复动作的所有者记录，不要求每层重复；诊断须脱敏，不暴露凭据或不必要的敏感载荷。

## Fitness Functions

- 识别值得持续保护、可明确判断的不变量，例如依赖方向、无环依赖、公共契约或已有体积预算；在本次授权范围内能用现有工具低成本验证时，主动放入已有检查入口，不等架构退化后再补。
- 写清检查的对象、预期与维护位置，验证它能发现目标违例；没有可靠指标、成本明显过高或需要新增体系时，说明限制，不擅自造框架或全仓门禁。
- 检查真实属性，不把方法名称或预期正文逐字固化为门禁；可复用编译器、类型系统和已有检查时，不重复造规则。

## 风险与证据

| 修改风险 | 最小相关证据 |
| --- | --- |
| 文案或规则格式 | diff、链接或格式检查；声称渲染正确时须有实际渲染证据。 |
| 局部逻辑或 Bug | 聚焦行为/回归测试，以及项目要求的相关根级检查。 |
| 公共契约或跨消费者迁移 | 契约与集成检查，覆盖真实消费者和退出的旧路径。 |
| 权限、金钱或持久化 | 成功、拒绝、失败/恢复边界，验证无越权或意外副作用。 |
| UI 或设备交互 | 语义化控件、可访问名称、键盘可达、可见焦点和信息不只依赖颜色；视觉、系统或设备结论需要对应实际验收。 |

使用已有包管理器、锁文件与根级脚本；缺少脚本时先读配置，不臆造命令或引入新测试框架。优先有限、可终止的检查；通过后只因新增变化、失败或未解决风险追加检查，不主动启动长期服务。

## 双轴审查

分别回答两个问题，不能互相替代：

- **需求轴**：是否满足已确认目标、成功判据、相关边界与必须保持的行为？
- **工程轴**：是否符合项目规则、正确所有权、清晰契约、维护性、安全和验证要求？

项目标准优先；代码气味是调查线索，不是自动重构命令。发现问题给出位置、可复现影响、严重度和最小正确修复方向。

## 交付核对

- 对照用户目标和必须保持的行为；diff 不带无关改动、调试输出、临时配置、注释旧代码及本次产生的未使用依赖或无消费者分支，保持用户 Git 边界。
- 报告真实命令、结果与覆盖范围，区分静态、单元、集成及人工/设备验收。不把单例通过说成稳定性证明，不把字节数直接称为 token 数。
