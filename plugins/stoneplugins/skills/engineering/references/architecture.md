# 架构与信任边界

涉及职责、接口、领域、依赖、信任边界或难以逆转的方案时读取。核心原则持续共同作用；以下条款将其具体化，不把整套方法设为开关，也不要求每次增加结构。

## 真实边界与深模块

- 先查明不变量、输入输出、状态所有者、真实消费者与部署依赖，以及失败时的原子性、幂等、补偿或恢复要求；区分已确认演进与猜测。可查明的事实先查。
- 用小而稳定的公共面隐藏策略和内部协调；跨边界只交换用例需要的数据与行为，不读取对方内部状态，不增加只透传调用的层。
- 同一业务事实由一个权威所有者维护，派生值优先计算；需要散落同步修改或双向同步状态时，调查所有权与边界。性能优化依据复杂度、测量或可复现瓶颈。

## SOLID 与整洁、六边形架构

领域独立、依赖方向、职责和契约始终参与设计；分别判断它们作用于什么对象，不以已有多个实现或反复维护痛点为统一前提。

| 原则 | 具体动作与边界 |
| --- | --- |
| SRP | 按独立变化原因和业务所有者聚合职责；多个步骤可以共同实现一个职责，不按函数长度、动作或文件数量机械拆分。 |
| OCP | 有真实变化轴或已确认演进方向时，主动评估最小组合点、策略或扩展接缝，不等反复返工；保护值得稳定的契约，不阻止纠正已证错误的契约。只有能降低当前或已确认演进成本时才建立，不为假想扩展造插件系统。 |
| LSP | 保持调用方依赖的共同契约：不收紧输入前提，不削弱输出与不变量，保持错误、取消、超时、重试、幂等和副作用语义；额外能力显式表达，让调用方有意选择，不用静默默认值伪装等价。 |
| ISP | 按真实消费者需要的能力划分公共面；存在能力差异即可分开，不必等多类消费者或重复痛点。可用函数、类型或模块表达，不强制每个能力一个文件、每个方法一个接口。 |
| DIP | 由稳定业务侧定义并拥有所需契约，易变 I/O、框架或供应商实现依赖该契约；抽象可以是函数或普通模块，不以增加接口和映射层证明依赖倒置。 |

单一实现也可以因当前领域隔离、易变外部边界、确定性测试或已确认替换而值得建立接缝。普通模块已能承担这些边界时直接使用；Port、Adapter、Use Case 只承载实际责任，不为目录形式增加空层。

## DDD 与领域边界

- 持续使用业务场景可验证的领域语言，明确不变量与所有权；不等领域足够复杂才理解语义，也不以技术层名称替代业务概念。
- 同一术语具有不同不变量或生命周期时分别建模，明确 Bounded Context；不要用统一模型抹平真实差异。跨 Context 明确翻译所有者、最小交换契约和失败处理责任，需要表达这些关系时记录 Context Map。
- Aggregate、Repository、Domain Service 分别服务实际的一致性、持久化和协调责任；没有对应责任时不造战术模式目录，普通模块足够时保留普通模块。

## Functional Core / Imperative Shell

- 对清晰的确定性业务决策，默认主动与 I/O 分离，不等大量 mock 或维护痛点出现：Core 接收显式数据，返回决定、状态变化描述或待执行动作；Shell 收集输入、读取时间或随机值、执行副作用并提交结果。
- 用可独立调用的纯函数或已有纯模块承载这类决策，使其验证不必执行外部服务或读取时钟；不必新增文件、接口族或框架。仅把服务作为参数传入 async 函数，或在同一函数内把计算与 I/O 分段，不等于已经分离；简单数据直通且没有独立业务决定时，不为形式抽取函数。
- 事务状态机、actor、流式协议和资源生命周期可保留更自然的模型，不强求全部纯函数；已有模块已清晰分开职责时复用，不再叠加等价的“纯函数层”。

## 组件内聚与耦合原则

每项原则按自己的对象持续应用：已有共同变化、复用消费者或依赖关系即可判断，不必先独立发布或出现依赖环；没有发布需求时不制造发布结构。

| 原则 | 具体动作与边界 |
| --- | --- |
| REP | 复用单元应有一致、可追踪的发布与版本边界；按实际复用和交付关系确定粒度，不为单独发布而拆包。 |
| CCP | 因同一原因、在同一时间变化的内容放在共同组件，减少一次业务改变散落到无关位置。 |
| CRP | 不会共同复用的能力，不强迫消费者共同依赖或承担无关升级。 |
| ADP | 维护模块与组件依赖图无环；发现环时调查所有权和依赖方向，不靠搬文件掩盖。 |
| SDP | 依赖指向相对稳定的组件，避免稳定业务被易变细节牵动。 |
| SAP | 用与组件稳定度相称的抽象保护稳定、被依赖的契约，不把稳定机械等同于更多接口。 |

REP、CCP 倾向聚合，CRP 倾向分开；以实际变化、复用和交付关系权衡，不以组件越细或越大作为目标。

## 信任边界与副作用

- 对涉及认证、授权、敏感数据或外部信任边界的变更，按本次范围做 Threat Modeling：列明参与者、数据流、边界、滥用路径、对应措施与验证；不扩张成无关安全工程。
- 在外部输入处验证结构和业务语义。数据库使用参数化查询，子进程传独立参数，输出按目标上下文编码；不以类型断言代替校验。
- 权限在可信端由资源所有者执行，并遵循最小权限；隐藏 UI 不是授权。沿用已有运行时凭据机制和最短必要生命周期，不把真实 Secret 放入代码、提交、测试夹具、日志、错误或回复。
- 对外错误只提供必要恢复信息；内部诊断脱敏。只收集和保留任务需要的数据，不为排障复制整份敏感载荷。
- 外部调用设有限超时和取消边界；超时不代表没有发生副作用。只有可证明安全重放的操作才能有限重试，必要时采用现有幂等、去重或恢复机制。
- 涉及支付、配额或高成本调用时，核对频率、并发、输入量和重试放大；成本估计与实测分开陈述。

## 方案比较、记录与持续保护

- 公共 API、数据模型、持久化格式或跨系统契约等重要决定难以逆转时，用 Design It Twice 比较至少两个真正不同的可行方案；约束只剩一个方向时说明排除依据，不制造陪衬方案。比较正确性、变化局部性、接口泄漏、维护复杂度、已确认演进及迁移恢复成本。
- 方案比较与记录分别判断：重要、长期有效且代码不足以解释的取舍留下简短持久记录，优先更新既有权威文档；确有独立记录价值或项目要求时才新增 ADR，不为每次比较机械建档。
- 已授权范围内完成调查和推荐；发现未知关键消费者、未获授权的数据风险或范围外实施时先说明并确认。长期正确方案可以是破坏性重构，执行仍遵守迁移与恢复边界。
- 有价值且可低成本测量的架构不变量，主动用已有工具和检查入口保护，不等违反后补救；具体 Fitness Functions 做法见 [verification.md](verification.md)。
