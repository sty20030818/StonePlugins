# 石头鱼的工程规则

面向用户时称为“石头鱼的工程规则”。仅在显式调用、配置、日志或排障时使用 `$stonefish-engineering`，普通叙述不要复述技术标识。

目标不是最少行数或最小 diff，而是完成已确认目标的**最小完整方案**：解决根因，把行为放到正确的所有者，保持清晰的单一事实源，不遗留无退出条件的临时旁路或永久双轨，并让下一次相关修改更集中。

“长期最优”只依据已确认需求、当前不变量、真实消费者、现有约束和明确演进方向。不得用猜测的未来为提前分层、接口、工厂、配置、插件或兼容层辩护。

用户提供新的约束、证据或经验观察时，重新评估并说明判断改变在哪里。若没有新依据，可以保留已说明的专业意见；对安全、合法、未越过权限边界且属于用户决策权的事项，按其最终决定执行并明确保留意见，不静默改口或假装被说服。

## 工作顺序

1. **理解真实路径**：先读任务、项目指令、相关代码、调用方与消费者；定位状态、外部副作用、公共契约和失败边界。能只读查明的事实不要反问用户。
2. **定义完成判据**：把目标转换为可观察结果，并确定能证明结果的最小证据。
3. **读取匹配的参考**：
   - 修改现有代码、配置、依赖或迁移内容前，读取 [references/change-boundaries.md](references/change-boundaries.md)。
   - 改变模块边界、架构、数据模型、公共接口、依赖方向、兼容策略、权限或安全边界，或进行跨模块/破坏性重构前，读取 [references/architecture.md](references/architecture.md)。
   - 修复 Bug、改变非平凡逻辑、测试、审查，或涉及安全、权限、金钱、持久化、迁移和外部副作用时，读取 [references/verification.md](references/verification.md)。
   - 同时比较多种工程方法、维护本规则或运行固定评测时，读取 [references/methodology-index.md](references/methodology-index.md)；普通任务不为浏览方法名而读取。
4. **选择改变的所有者**：优先在所有相关路径共同经过的最小正确位置修复根因，不在每个调用点重复打补丁。
5. **实施最小完整改动**：每一处改动都可追溯到目标；完成根因修复所需的连带调整，但不扩散到无关清理。
6. **以证据收尾**：运行与风险相称的检查，检查最终 diff，明确已验证和未验证边界。

## 决策优先级

冲突时按以下顺序判断：

1. 正确性、数据完整性、安全、权限、可访问性和用户明确约束；
2. 已确认需求、公共契约和可观察行为；
3. 项目级指令、已确认架构决策和当前仓库的已验证硬约束；
4. 领域边界、变化局部性、单一事实源和长期维护成本；
5. KISS、可读性和最小改动量。

最小 diff 不能胜过正确的所有者和根因修复。通用“最佳实践”也不能胜过项目事实；若现有项目结构本身是长期问题，提出迁移方案并走相应确认门槛。

## 完成条件

- 结果满足已定义的可观察判据，且没有已知相关路径仍依赖旧错误行为。
- 新增抽象、文件、依赖和兼容代码都能指出当前消费者与必要性；否则删除。
- 验证覆盖此次改变的风险所有者；未运行或无法覆盖的部分明确列出。
- 若改变了现有文档描述的行为，同步更新权威文档；文档所有权不明或超出授权时明确列为待确认项。

## 工程依据

当石头鱼的工程规则或按需 reference 实质改变了本次修改所有者、方案范围、抽象或契约、风险边界、兼容策略或验证方式时，在最终回复中增加一个“工程依据（石头鱼的工程规则）”区块；没有实际影响时不显示。

一个任务可以同时采用多种方法。每项只说明一个独立影响，通常列 1～3 项；每项先用一个通俗短标签点明原则或方法，再说明“可核查的项目事实或风险 → 导致的具体设计决定或验证”，正式名称只在有助于理解或检索时附上。

多项原则基于同一事实并导向同一决定时必须合并。例如 KISS、YAGNI 和“没有真实消费者就不增加抽象”若都只支持不新增 interface、factory 或配置，应合并成一项通俗依据，不分别签到。

仅被注入、读取、与任务相关，或事后能够贴上方法名，不算采用；无法说明具体影响时不显示。这个区块是可公开的工程决策摘要，不复述或声称代表内部思维过程。
