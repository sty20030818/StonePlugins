# 长期工程准则

目标不是最少行数或最小 diff，而是完成已确认目标的**最小完整方案**：解决根因，把行为放到正确的所有者，保持一个清晰事实源，不遗留无退出条件的临时旁路或永久双轨，并让下一次相关修改更集中。

“长期最优”只依据已确认需求、当前不变量、真实消费者、现有约束和明确演进方向。不得用猜测的未来为提前分层、接口、工厂、配置、插件或兼容层辩护。

## 工作顺序

1. **理解真实路径**：先读任务、项目指令、相关代码、调用方与消费者；定位状态、外部副作用、公共契约和失败边界。能只读查明的事实不要反问用户。
2. **定义完成判据**：把目标转换为可观察结果，并确定能证明结果的最小证据。
3. **读取匹配的参考**：
   - 修改现有代码、配置、依赖或迁移内容前，读取 [references/change-boundaries.md](references/change-boundaries.md)。
   - 改变模块边界、架构、数据模型、公共接口、依赖方向、兼容策略、权限或安全边界，或进行跨模块/破坏性重构前，读取 [references/architecture.md](references/architecture.md)。
   - 修复 Bug、改变非平凡逻辑、测试、审查，或涉及安全、权限、金钱、持久化、迁移和外部副作用时，读取 [references/verification.md](references/verification.md)。
4. **选择改变的所有者**：优先在所有相关路径共同经过的最小正确位置修复根因，不在每个调用点重复打补丁。
5. **实施最小完整改动**：每一处改动都可追溯到目标；完成根因修复所需的连带调整，但不扩散到无关清理。
6. **以证据收尾**：运行与风险相称的检查，检查最终 diff，明确已验证和未验证边界。

## 决策优先级

冲突时按以下顺序判断：

1. 正确性、数据完整性、安全、权限、可访问性和用户明确约束；
2. 已确认需求、公共契约和可观察行为；
3. 项目级指令、已确认架构决策和当前仓库的已验证硬约束；
4. 领域边界、变化局部性、单一事实源和长期维护成本；
5. KISS、可读性和最小改动量。

最小 diff 不能胜过正确的所有者和根因修复。通用“最佳实践”也不能胜过项目事实；若现有项目结构本身是长期问题，提出迁移方案并走相应确认门槛。

## 完成条件

- 结果满足已定义的可观察判据，且没有已知相关路径仍依赖旧错误行为。
- 新增抽象、文件、依赖和兼容代码都能指出当前消费者与必要性；否则删除。
- 验证覆盖此次改变的风险所有者；未运行或无法覆盖的部分明确列出。
