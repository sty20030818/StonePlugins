# 架构与长期变更

只在任务涉及模块边界、公共接口、数据模型、依赖方向、权限或安全边界、跨模块重构、迁移或兼容策略时读取本文件。它是决策检查表，不要求所有项目套同一分层图。

## 先确认真实边界

在提方案前确认：

- 哪些业务不变量必须始终成立，谁拥有它们；
- 哪些调用方、外部消费者、存量数据和部署环境真实存在；
- 状态的唯一事实源在哪里，谁能修改；
- 哪些是纯领域决策，哪些是 I/O、框架、数据库、第三方服务或 UI 细节；
- 失败时需要原子性、幂等、重试、补偿、回滚还是人工恢复；
- 哪些未来方向已经确认，哪些只是推测。

如果这些事实能从代码、契约、运行证据或文档查明，先查；只有会改变方向且无法查明的缺口才询问。

## 原则必须改变决策

- **第一性原则**：先写清不变量、输入输出、拥有者和失败语义，再选择模式、分层或库。
- **KISS / YAGNI**：减少概念、状态源、依赖和维护路径；不实现未确认功能，不为单次场景创建抽象或扩展点。
- **DRY**：消除同一业务知识需要同步修改的重复，不机械合并长得相似但变化原因不同的代码。小规模重复可以保留，直到共享规则和共同变化真实稳定。
- **单一职责**：按变化原因与业务所有者划分职责，不按函数长度、文件数量或描述中是否出现“和”机械拆分。
- **高内聚、低耦合**：同一业务决定集中；跨边界只交换完成任务所需的最小数据与行为，不读取对方内部状态。
- **模块化、组件化**：用边界隐藏复杂度，不以增加文件、接口和中间层为目标。
- **局部性**：一次业务规则变化应尽量集中在一个所有者；若需要散落修改多处，调查边界或事实源是否错误。
- **性能**：以数据、复杂度分析或可复现瓶颈为依据；不以想象中的收益交换长期复杂度。
- **信任边界**：不可信输入在进入可信域时验证；授权由拥有资源的可信端执行，不能用 UI 隐藏或客户端判断代替；凭据遵循最小权限且不得进入日志或错误输出。

## 用变化局部性设计

- **领域语言**：使用业务中稳定、可由场景验证的术语；同一概念不要在不同层使用含义漂移的名字。
- **职责与所有权**：按业务决定和变化原因聚合代码。一个模块可以执行多个步骤，只要它们共同实现一个职责；不要按动作数量机械拆分。
- **深模块与信息隐藏**：优先让一个小接口隐藏较多策略与复杂度。只转发参数、要求调用方理解内部顺序的薄层通常不值得存在。
- **公共接口**：暴露完成用例所需的最小稳定表面，并通过该表面验证行为。显式公共表面不等于所有语言都必须使用 barrel 文件。
- **依赖方向**：让稳定的业务规则少受易变基础设施影响，但不要为了画出“干净”层级制造无行为接口和映射层。
- **单一事实源**：同一业务事实只由一个权威所有者维护；派生值尽量计算，不建立需要双向同步的第二状态。

## 何时使用整洁架构或六边形架构

当以下至少一个条件真实存在时，端口/适配器或依赖倒置可能有价值：

- 领域规则复杂且需要独立于框架或 I/O 验证；
- 存储、支付、消息、远程 API 等外部边界由不同团队或供应商拥有，变化和失败语义需要隔离；
- 已有多个承担同一角色、可替换且共享稳定行为契约的真实实现或适配器；
- 已确认会替换实现，且替换成本高于维护边界的成本；
- 测试必须替换不可控外部依赖，而直接的模块边界不足以做到。

只有一个实现、一个调用点和简单 CRUD 时，优先把第三方细节封装在普通模块中；不要先造 port、adapter、factory、DTO 映射和 use-case 层。

多个真实实现是接缝成立的强证据，但不是必要条件。单一实现只有在复杂领域隔离、易变外部边界或确定性测试能带来当前价值时才建立端口。

整洁/六边形架构的目标是保护重要业务规则和降低变化扩散，不是让目录名称看起来标准。

## 抽象与 DRY 的门槛

只有在抽象能减少当前认知或维护成本时才引入。至少应满足一项：

- 多处代码表达同一业务知识，修改时必须同步；
- 已有多个真实消费者或实现共享稳定契约；
- 当前职责混杂导致独立变化互相影响；
- 复杂策略可以被隐藏在更小的接口后；
- 已确认演进方向使边界现在就有明确价值。

不要因两段代码语法相似就合并。不要用配置、泛型、继承或插件系统替代尚未出现的需求。

## 高成本决策

公共 API、数据模型、持久化格式、模块所有权和跨系统契约难以逆转时，若存在真实可行替代，比较至少两个真正不同的方案；若约束只留下一个可行方案，说明其他方向为何被排除。按以下维度给出推荐：

- 正确性与不变量；
- 变化局部性与认知负担；
- 接口深度和泄漏程度；
- 数据、部署、兼容和回滚成本；
- 当前复杂度与已确认演进需求。

只有存在真实取舍、决定难以逆转且未来维护者无法从代码理解“为什么”时，才记录简短 ADR；不要为普通实现细节写文档仪式。

## 架构坏味道

以下现象是调查信号，不是自动重构命令：

- 一条业务规则变化需要在许多无关文件重复修改；
- 同一事实存在多个可写来源；
- 模块主要是透传、转换同一数据或暴露内部顺序；
- 领域规则散落在控制器、UI、数据库回调和第三方适配代码中；
- 循环依赖、跨模块内部导入或调用方必须了解实现细节；
- 为一个实现建立完整接口族，或为想象中的未来增加配置和扩展点；
- 旧路径、feature flag 和兼容分支没有消费者或退出计划。

先用真实调用路径和变化历史验证坏味道，再决定是局部修复、边界调整还是经确认的迁移。
