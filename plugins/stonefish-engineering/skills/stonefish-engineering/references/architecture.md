# 架构与长期变更

只在任务涉及模块边界、公共接口、数据模型、依赖方向、权限或安全边界、跨模块重构、迁移或兼容策略时读取本文件。常驻原则已由核心契约共同应用；本文件只补充有真实信号时的具体架构方法，不要求所有项目套同一分层图。

## 先确认真实边界

在提方案前确认：

- 哪些业务不变量必须始终成立，谁拥有它们；
- 哪些调用方、外部消费者、存量数据和部署环境真实存在；
- 状态的唯一事实源在哪里，谁能修改；
- 哪些是纯领域决策，哪些是 I/O、框架、数据库、第三方服务或 UI 细节；
- 失败时需要原子性、幂等、重试、补偿、回滚还是人工恢复；
- 哪些未来方向已经确认，哪些只是推测。

如果这些事实能从代码、契约、运行证据或文档查明，先查；只有会改变方向且无法查明的缺口才询问。

## 原则必须改变决策

- **第一性原则**：先写清不变量、输入输出、拥有者和失败语义，再选择模式、分层或库。
- **KISS / YAGNI**：减少概念、状态源、依赖和维护路径；不实现未确认功能，不为单次场景创建抽象或扩展点。
- **知识级 DRY**：消除同一业务知识需要同步修改的重复，不把“代码长得一样”当作充分理由。变化原因独立的相似代码可以保留，直到共享规则和共同变化真实稳定。
- **单一职责**：按变化原因与业务所有者划分职责，不按函数长度、文件数量或描述中是否出现“和”机械拆分。
- **高内聚、低耦合**：同一业务决定集中；跨边界只交换完成任务所需的最小数据与行为，不读取对方内部状态。
- **模块化、组件化**：用边界隐藏复杂度，不以增加文件、接口和中间层为目标。
- **局部性**：一次业务规则变化应尽量集中在一个所有者；若需要散落修改多处，调查边界或事实源是否错误。
- **性能**：以数据、复杂度分析或可复现瓶颈为依据；不以想象中的收益交换长期复杂度。
- **信任边界**：不可信输入在进入可信域时验证；授权由拥有资源的可信端执行，不能用 UI 隐藏或客户端判断代替；凭据遵循最小权限且不得进入日志或错误输出。

## 安全与隐私基线

- 真实机密不得硬编码或进入提交、日志、错误、测试夹具、聊天回复及其他面向用户输出；使用项目既有的密钥管理或运行时注入方式，并按最小权限和最短必要生命周期处理。
- 在信任边界验证不可信输入的语法与业务语义；SQL 使用参数化查询，进程调用优先参数数组或结构化 API，输出按实际解释器和上下文编码。笼统“转义”不能替代对应边界的安全 API。
- 新增或修改授权时，由资源所有者在可信端强制执行并默认最小权限；客户端检查只能改善体验，不能充当授权边界。
- 认证、授权、敏感数据处理或新增外部信任边界时，至少梳理参与者、数据流、信任边界、可滥用路径以及对应缓解和验证；只做与当前变更相关的轻量威胁建模，不要求每次重画全系统。
- 对外错误只暴露调用方恢复所需的信息；内部诊断受控、脱敏且避免重复记录。日志、遥测、错误报告和模型输入只包含完成目的所需的数据。

## 外部副作用与失败安全

- 外部调用应设置与业务语义匹配的有限超时并正确传播取消。重试必须有上限，并证明操作可安全重放；非幂等副作用使用幂等键、去重、状态机或明确恢复流程避免重复执行。
- 修改付费或受配额限制的外部调用路径时，评估调用频率、输入规模、并发、重试和缓存对成本与限额的影响，并区分估算与实测。

## 用变化局部性设计

- **领域语言**：使用业务中稳定、可由场景验证的术语；同一概念不要在不同层使用含义漂移的名字。
- **职责与所有权**：按业务决定和变化原因聚合代码。一个模块可以执行多个步骤，只要它们共同实现一个职责；不要按动作数量机械拆分。
- **深模块与信息隐藏**：优先让一个小接口隐藏较多策略与复杂度。只转发参数、要求调用方理解内部顺序的薄层通常不值得存在。
- **公共接口**：暴露完成用例所需的最小稳定表面，并通过该表面验证行为。显式公共表面不等于所有语言都必须使用 barrel 文件。
- **依赖方向**：让稳定的业务规则少受易变基础设施影响，但不要为了画出“干净”层级制造无行为接口和映射层。
- **单一事实源**：同一业务事实只由一个权威所有者维护；派生值尽量计算，不建立需要双向同步的第二状态。

## 何时使用整洁架构或六边形架构

当以下至少一个条件真实存在时，端口/适配器或依赖倒置可能有价值：

- 领域规则复杂且需要独立于框架或 I/O 验证；
- 存储、支付、消息、远程 API 等外部边界由不同团队或供应商拥有，变化和失败语义需要隔离；
- 已有多个承担同一角色、可替换且共享稳定行为契约的真实实现或适配器；
- 已确认会替换实现，且替换成本高于维护边界的成本；
- 测试必须替换不可控外部依赖，而直接的模块边界不足以做到。

只有一个实现、一个调用点和简单 CRUD 时，优先把第三方细节封装在普通模块中；不要先造 port、adapter、factory、DTO 映射和 use-case 层。

多个真实实现是接缝成立的强证据，但不是必要条件。单一实现只有在复杂领域隔离、易变外部边界或确定性测试能带来当前价值时才建立端口。

整洁/六边形架构的目标是保护重要业务规则和降低变化扩散，不是让目录名称看起来标准。

## Functional Core / Imperative Shell

当业务判断与 I/O、时间、随机性、远程调用或可变状态交错，导致同一规则难以复用、测试依赖大量 mock 或失败边界模糊时，可以把确定性决策放进 Functional Core，把读取、写入、事务和外部副作用留在 Imperative Shell。

- Core 接收显式数据并返回决定、状态变化描述或待执行动作；Shell 负责收集输入、执行副作用和提交结果。
- 不要求业务全部写成纯函数。事务状态机、actor、流式协议或资源生命周期明显更自然时，保留合适模型。
- 不建立与现有普通模块等价的“纯函数层”；只有隔离确实提高复用、确定性验证或失败处理时才拆分。

## DDD 与领域边界

DDD 只在领域复杂度真实存在时使用。先采用领域语言，再根据冲突决定是否需要更强结构：

- 代码、事件和接口使用业务参与者能验证的稳定术语，不以技术层名称替代领域概念。
- 同一术语在不同业务区域拥有不同不变量或生命周期时，分别建模并明确 Bounded Context；不要用一个“大一统模型”消除真实差异。
- 跨 Context 交互时说明谁负责翻译、共享哪些最小契约、失败如何处理；需要时记录 Context Map，不复制双方内部模型。
- Aggregate、Repository、Domain Service 等战术模式只有在对应不变量、持久化或协调问题存在时才采用，不建立模式目录。

简单 CRUD、通用基础设施或没有专属业务语言的工具不需要 DDD 结构。

## SOLID 的条件部分

SRP 和正确依赖方向已由常驻契约持续应用；其余原则只在相应关系真实存在时具体化：

- **OCP**：已观察到稳定变化轴，且直接修改核心契约造成反复风险时，才建立组合点或扩展接缝；不为假想扩展设计插件系统。
- **LSP**：多个实现声称可以替换时，以调用方依赖的行为契约判断可替换性，而不只看类型形状。
- **ISP**：不同消费者只需要不同能力，且大接口迫使它们依赖无关行为时，按消费者契约拆分；不是把每个方法拆成一个接口。
- **DIP**：稳定领域规则需要隔离易变或不可控依赖时，让抽象由稳定一侧拥有；单一简单实现没有隔离价值时使用普通模块封装。

不要为了补齐 SOLID 缩写而制造接口、继承层或映射代码。

## 组件内聚与耦合原则

只有当 Package 具备独立发布、跨团队复用或明显依赖图时，才使用组件级原则决定打包和依赖：

- **REP**：独立复用的最小粒度应能独立发布和追踪版本。
- **CCP**：因同一原因、在同一时间变化的内容放在同一组件。
- **CRP**：不会被一起复用的能力不要强迫消费者共同依赖。
- **ADP**：组件依赖图不得形成环；发现环时先调查所有权和稳定方向。
- **SDP**：依赖指向相对稳定的组件，避免稳定组件被易变细节拖动。
- **SAP**：被广泛依赖且必须稳定的组件，用与其稳定度相称的抽象保护；稳定不等于盲目增加接口。

REP、CCP 倾向让组件变大，CRP 倾向让组件变小。根据当前发布和复用事实权衡，不能把“越细越模块化”当作目标。普通目录分文件不使用这套发布级判断。

## 架构 Fitness Functions

当项目已经有明确、可自动测量的架构质量属性时，把最重要的不变量变成持续检查，例如禁止依赖反向、限制循环依赖、验证公共契约或控制包体积。指标必须对应真实失败模式并有清晰所有者；没有项目特有目标时，不把抽象口号改造成脆弱的正则门禁。

## 可替换实现的行为契约

当同一 interface、port 或协议存在多个实现、provider、adapter 或 test double 时，类型兼容只证明调用形状，不证明行为可以替换。所有实现应保持调用方依赖的同一契约：

- 不偷偷收紧有效输入、调用顺序或运行环境等前置条件；
- 不削弱输出、状态变化和业务不变量等后置条件；
- 保持调用方可观察的错误分类、取消、超时、重试、幂等和关键副作用语义；
- test double 不得通过忽略生产实现必须承担的失败或副作用，制造虚假通过；
- 通过同一公共边界运行共享 contract tests，各实现再补自己的特有能力和集成风险。

若实现的能力或保证确实不同，应拆分或显式表达能力契约，让调用方有意选择；不要把不可替换的实现硬塞进同一抽象。没有真实替换关系时，也不为补齐 SOLID 缩写而建立接口族。

## 抽象与 DRY 的门槛

只有在抽象能减少当前认知或维护成本时才引入。至少应满足一项：

- 多处代码表达同一业务知识，修改时必须同步；
- 已有多个真实消费者或实现共享稳定契约；
- 当前职责混杂导致独立变化互相影响；
- 复杂策略可以被隐藏在更小的接口后；
- 已确认演进方向使边界现在就有明确价值。

不要因两段代码语法相似就合并。不要用配置、泛型、继承或插件系统替代尚未出现的需求。

## 高成本决策

公共 API、数据模型、持久化格式、模块所有权和跨系统契约难以逆转时，使用 Design It Twice 比较至少两个真正不同的方案；若约束只留下一个可行方案，说明其他方向为何被排除。按以下维度给出推荐：

- 正确性与不变量；
- 变化局部性与认知负担；
- 接口深度和泄漏程度；
- 数据、部署、兼容和回滚成本；
- 当前复杂度与已确认演进需求。

只有存在真实取舍、决定难以逆转且未来维护者无法从代码理解“为什么”时，才记录简短 ADR；不要为普通实现细节写文档仪式。

## 架构坏味道

以下现象是调查信号，不是自动重构命令：

- 一条业务规则变化需要在许多无关文件重复修改；
- 同一事实存在多个可写来源；
- 模块主要是透传、转换同一数据或暴露内部顺序；
- 领域规则散落在控制器、UI、数据库回调和第三方适配代码中；
- 循环依赖、跨模块内部导入或调用方必须了解实现细节；
- 为一个实现建立完整接口族，或为想象中的未来增加配置和扩展点；
- 旧路径、feature flag 和兼容分支没有消费者或退出计划。

先用真实调用路径和变化历史验证坏味道，再决定是局部修复、边界调整还是经确认的迁移。
