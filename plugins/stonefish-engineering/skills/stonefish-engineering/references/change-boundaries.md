# 修改边界、依赖与迁移

修改现有代码、配置、依赖或迁移内容前读取本文件。目标是允许完整根因修复，同时保护任务范围、用户状态和真实消费者。

## 外科手术式修改与 Boy Scout Rule

两者不冲突：外科手术式修改限定**因果边界**，Boy Scout Rule 改善**边界内的质量**。

因果边界由用户目标、真实调用链、共享状态和消费者决定，不由“本次打开了哪些文件”决定。每一处改动都应能追溯到当前目标。

边界内允许：

- 在所有相关路径共同经过的位置修复根因；
- 统一同一业务事实的重复状态源或重复规则；
- 清理本次改动产生的孤儿、死分支和未使用依赖；
- 调整妨碍正确实现或验证的局部结构；
- 删除已证明仅属内部、无消费者且位于已授权范围内的旧路径；涉及外部消费者时先确认迁移策略。

边界外不做：

- 仅因“刚好看到”而格式化、重命名、重写注释或整理目录；
- 修复与当前目标无因果关系的历史坏味道；
- 未经消费者审计删除公共 API 或行为；
- 把局部任务扩成全仓风格统一、依赖升级或架构迁移。

无关问题可以报告。用户明确授权重构、整理或迁移后，因果边界可以扩大，但仍只改为该目标服务的内容。

任务外问题默认在交付中报告，不为“防止忘记”而擅自修改代码。只有项目已指定 issue、债务清单等持久载体且用户授权时才写入；仅对本次改动主动留下的已知限制，可按项目惯例记录影响、负责人或引用以及退出条件。

## Tidy First：结构改动与行为改动

先区分本次改动是在改变可观察行为，还是在不改变行为的前提下整理结构。只有一个小型、可验证、可回退的结构调整会明显降低本次行为修改的风险或扩散范围时，才先整理；否则先完成行为目标，再在同一因果边界内决定是否整理。

- 结构调整前后分别运行能证明行为保持的检查；行为修改再用目标对应的证据验证，不让两类变化互相掩盖。
- 不要求为了形式把两类变化拆成未经授权的独立 commit，但最终 diff 应让审查者能够区分目的和证据。
- rename、extract、move 等小调整可以是整理；拆服务、迁移数据、改变公共契约等难以逆转的动作仍按高成本决策和确认门槛处理，不能借“先整理”绕过。
- Boy Scout Rule 只改善当前因果边界；Tidy First 只回答边界内结构与行为的先后，不扩大任务范围。

## 最小完整改动

若最小局部补丁会保留错误所有权、第二事实源、重复业务分支、shotgun surgery 或已知返工，应提出能闭合根因的最小连贯重构。

反过来，不因“长期”猜测未来：没有真实消费者、重复变化或确认方向时，不增加工厂、接口、配置、插件、扩展点和兼容层。

按以下顺序检查是否已有合适能力：仓库现有实现 → 标准库或平台原生能力 → 已安装依赖 → 最小自有实现 → 新依赖。最终按正确性、项目适配、维护与安全成本选择，不为复用而复用。

## 依赖与工具链

- 引入新依赖前证明前述能力不能合理解决，并说明项目适配、文档与生态成熟度、维护、安全、体积、升级、退出以及适用的许可证和分发成本。
- 工具选择优先级：项目不可违反的硬约束和已确认契约 → 当前任务明确授权的目标 → 未要求改变时沿用既有工具链 → 无约定时选择合适工具并说明假设。
- 未明确授权工具链迁移时，沿用现有项目的包管理器、锁文件和根级脚本；依赖变更同步更新声明与锁文件，不手工制造无关锁文件变化，不擅自切换工具链或臆造脚本。
- 项目已锁定版本时，优先查对应版本的官方文档；选型、升级或判断当前生态状态时再查当前官方资料。
- 命名、格式和注释遵循仓库及周边代码惯例；注释只解释契约、业务规则或不明显的原因。

## 文档同步

若本次改动改变了现有 README、接口说明、SOP、示例或架构决策所描述的行为，同步更新其权威来源。无法确认文档所有权，或更新会超出已授权范围时，不静默猜测，明确列为待确认项。

## 破坏性重构与兼容性

破坏性重构可以是长期推荐方案，但不是默认权限。执行前列出：

1. 所有已知调用方、外部消费者和公共契约；
2. 存量数据、配置、自动化与部署依赖；
3. 迁移和切换顺序、停机影响、失败恢复与回滚边界；
4. 需要同步修改和删除的代码、测试、配置、依赖与文档；
5. 保持的行为与明确改变的行为；
6. 证明旧路径无消费者和新路径正确的验证方式。

当前请求已明确授权且影响仍在已说明范围内时，不重复确认；发现外部消费者、数据风险或影响超出授权范围时，先停止并确认。

根据阻止干净切换的真实约束选择迁移手法，不把任何模式当作破坏性重构的默认答案：

| 约束 | 优先考虑 | 必须守住的边界 |
| --- | --- | --- |
| 所有消费者可在同一批次修改 | Clean cut | 同批迁移调用点、测试、配置和文档，并删除旧路径 |
| API 或 schema 消费者不能同时升级 | Parallel Change：expand → migrate → contract | 兼容面有负责人、迁移完成证据和删除时点 |
| 替换内部库、框架或 provider，同时主干持续交付 | Branch by Abstraction | 抽象只承担受控迁移；完成后重新证明长期价值，否则删除 |
| 大型遗留系统可按业务能力逐片替换 | Strangler Fig | 找到真实 seam 或拦截边界，管理新旧状态、路由、双写和退出条件 |
| 大型源码重构不断暴露未知前置条件 | Mikado Method | 用小型可恢复实验发现并记录依赖，不覆盖用户改动或依赖破坏性 reset |

若所有消费者能同步迁移，采用干净切换，删除旧实现、验证旧实现形状或失效行为的测试、旧依赖、feature flag 和零消费者兼容壳；仍有效的行为测试迁移到新公共边界，不保留永久双轨。

完成重命名、签名或调用协议迁移后，搜索旧符号和旧形状并审计全部已知消费者。搜索用于发现遗漏，不能代替公共契约和行为验证。

若存在外部消费者、分阶段发布或不可一次迁移的数据，兼容期必须是显式迁移策略，包含负责人、退出条件和删除时点。

兼容截止时间必须来自已确认的合同或发布计划；尚未确认时列为待决策，不擅自给出具体日期。

## 用户状态保护

- 仓库受版本控制时，修改前检查相关工作树状态；区分用户已有改动与本次改动。
- 不覆盖、回滚或格式化用户的无关改动；无法安全绕开时停止并说明冲突。
- 不擅自暂存、提交、推送、发布或写入范围外系统。
- 删除或覆盖物质性数据前精确核对目标、恢复方式和授权。
