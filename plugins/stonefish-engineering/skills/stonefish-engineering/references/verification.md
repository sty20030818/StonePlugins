# 验证、诊断与审查

只在任务改变行为、修复 Bug、包含非平凡逻辑，或涉及测试、审查、安全、权限、金钱、持久化、迁移和外部副作用时读取本文件。

## 先定义证据

开始前把目标写成可观察结果：什么输入、状态或操作应产生什么行为；什么旧问题必须不再出现；哪些行为必须保持。

验证强度与风险相称。不要把“穷尽所有情况”作为无法兑现的口号；明确覆盖的风险、代表性边界和未覆盖范围。

## Bug：先建立会变红的反馈环

1. 用最短稳定路径复现症状，或建立能在错误存在时失败的检查。
2. 沿真实调用链定位共同所有者和所有同类消费者。
3. 列出可证伪假设；一次只改变一个关键变量，收集能区分假设的证据。
4. 在最小正确边界修复根因，而不是只补工单描述的一个入口。
5. 在公共行为或正确接缝留下回归检查，再清理诊断代码和临时绕路。

无法稳定复现时，不要假装确认根因；说明当前证据、最可能解释和下一步最有区分度的检查。

## 测试行为，不测试实现形状

- 优先通过公共接口、用户可见行为或稳定模块接缝测试，不锁定私有函数、内部调用顺序和偶然 DOM/对象形状。
- 一个行为测试驱动一个最小实现切片；跨层功能优先做能贯穿真实路径的垂直切片，再扩展边界情况。
- 实现非平凡逻辑时，在任务授权范围且存在合适测试接缝的情况下留下可回归检查；否则明确未覆盖风险和最小人工验证方法。
- 重构应先保留行为证据；若旧测试只验证内部结构，用新边界上的行为测试替换，而不是叠加重复套件。
- 不为纯文案、显然的一行改动或编译器已经完整覆盖的事实强制新增测试。

## 按风险选择检查

| 变化 | 最小证据 |
| --- | --- |
| 纯文案、注释、无行为格式 | 检查最终 diff 与渲染/格式（若相关） |
| 局部逻辑或组件行为 | 聚焦测试；再按仓库要求运行类型、lint 或构建检查 |
| Bug 修复 | 修复前能失败、修复后能通过的回归证据；检查同类调用方 |
| 跨模块或公共契约 | 聚焦测试 + 契约/集成检查 + 受影响消费者审计 |
| 数据迁移、权限、安全、金钱 | 正反路径、边界输入、失败恢复或回滚证据；必要时更广验证 |
| UI/桌面真实交互 | 自动化只证明其覆盖范围；视觉、系统集成或真机行为需单独人工验收 |

优先使用项目已有的包管理器、锁文件和仓库根级脚本。不存在相应脚本时先读取项目配置，不臆造命令或擅自拆分 workspace 命令。

优先选择聚焦、可终止的检查；确实需要长期运行服务时，说明目的并遵循项目与用户的既有工作流。

## 双轴审查

审查时独立回答两个问题，不能互相替代：

1. **需求轴**：实现是否满足已确认目标、边界情况和成功判据？
2. **工程轴**：实现是否符合仓库规则、正确所有权、清晰契约、维护性、安全性和验证标准？

项目已记录的标准优先于通用代码气味；代码气味是调查线索，不是自动判错。发现问题时给出文件/位置、可复现影响、严重度和最小正确修复方向。

## 交付前检查

- 仓库受版本控制时，检查工作树和最终 diff，确认没有覆盖用户改动或混入无关格式化。
- 确认自己造成的未使用代码、旧分支、测试和依赖已处理；任务外的历史问题只报告。
- 记录实际运行的命令及结果。没有运行的检查不要写成通过。
- 明确区分：单元/聚焦测试、静态检查、构建、集成或端到端验证、真实应用/人工验收。
- 不因测试通过就宣称需求正确，也不因满足示例就宣称所有风险已覆盖。
